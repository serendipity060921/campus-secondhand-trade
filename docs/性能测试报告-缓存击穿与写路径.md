## 一、缓存击穿实验（热点 key 过期瞬间会发生什么）

### 1.1 为什么单独测这个

"缓存穿透 / 击穿 / 雪崩"三件套里，**击穿**最隐蔽：某个热点 key 恰好过期的那一瞬间，
如果所有请求都发现"缓存没了"并一起去查库，**数据库会被瞬间打穿**。
本项目的设计是「**互斥重建**」：用分布式锁（`cacheService.tryLock`）保证只放一个请求去查库并回填，
其余请求短暂等待后直接复用缓存。

本篇用可测量的方式回答一个问题：**这个保护真的生效了吗？**

### 1.2 方法（可复现）

```
① 预热：先请求一次，确保处于"有缓存"状态
② DEL 掉该 key —— 精确模拟"热点 key 恰好过期"
③ N 个线程在同一栅栏（barrier）后【同时】发起请求（真正的并发冲击，而非依次发出）
④ 用 MySQL `SHOW GLOBAL STATUS LIKE 'Questions'` 的增量衡量"这 N 个并发一共打了几次库"
```

**基线校准（关键）**：一次缓存重建往往不止一条 SQL（商品 + 卖家 + 图片等多张表），
因此不能简单用"增量==1"判读。先单独测出**一次重建的成本**作为基线，再用 `增量 ÷ 基线` 换算成
"实际发生了几次重建"。

本次基线：**一次缓存重建 ≈ 9 条数据库语句**。

### 1.3 结果

被测对象：商品详情 `GET /api/product/6`，Redis key `campus:product:detail:6`，并发 50，共 4 轮。

| 轮次 | 请求数 | 错误 | DB 语句增量 | 换算重建次数 | 总耗时 | P95 | 最大延迟 | 判定 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 50 | 0 | 13 | **1** | 98.3 ms | 87.3 ms | 87.6 ms | ✅ 互斥重建生效 |
| 2 | 50 | 0 | 8 | **1** | 102.4 ms | 90.5 ms | 91.7 ms | ✅ |
| 3 | 50 | 0 | 8 | **1** | 103.8 ms | 93.4 ms | 93.9 ms | ✅ |
| 4 | 50 | 0 | 8 | **1** | 100.9 ms | 90.8 ms | 90.8 ms | ✅ |

### 1.4 结论

> **50 个并发同时冲击同一个刚过期的热点 key，实际只发生了 1 次缓存重建** ——
> 若没有互斥保护，期望是 **50 次**；重复查库降低了约 **50 倍**，且全程 **0 错误**。

延迟分布也符合预期：50 个请求分成"1 个重建者（略慢）+ 49 个等待后复用"，
因此 P95 与最大值都稳定在 90 ms 左右，**没有出现尖刺**。

### 1.5 与前一份报告的关系

前一份《缓存效果对照》测的是**稳态吞吐**（开/关缓存下的 QPS 与数据库压力，
结论：数据库压力下降 99.93%）；本篇测的是**失效瞬间的冲击**。
两者合起来才完整回答"缓存到底靠不靠谱"：**平时省数据库，关键时刻也不打穿**。

## 二、写路径压测（收藏 / 取消循环）

### 2.1 设置

每个循环 = 1 次收藏写库 + 1 次取消写库 + 2 次缓存失效（`CacheEvictor.productChanged`）。
10 并发、持续 12 秒，统计循环数、QPS、延迟分位值与返回码分布。
脚本结束后自动清理本次产生的收藏记录（已验证演示数据不变量 `4/17/4/4/9` 保持完好）。

### 2.2 结果

| 指标 | 数值 |
| --- | --- |
| 循环数 | 6,887 |
| 每秒循环 | **576.1** |
| 平均延迟 | 17.32 ms |
| P95 | 33.93 ms |
| 最大延迟 | 369.28 ms |
| 异常（抛错） | **0** |
| DB 语句增量 | 369（DB QPS ≈ 30.9） |

### 2.3 ★ 关键观察：成功响应只有 1 次

返回码分布为 **`[429, 4001]`**：

- **429（操作过于频繁）** —— 写接口的**注解式限流**生效，把并发刷接口的请求挡在外面；
- **4001（已收藏该商品）** —— `favorite` 表唯一索引 `uk_user_product` 生效，
  多个并发线程对同一商品做"收藏/取消"切换时，重复的那一半被正确拒绝。

**这不是缺陷，而是两条设计在并发下正确生效的证据**：
限流保护接口、唯一约束保护数据。它们与本项目的单元测试
（`RateLimitAspectTest`、`FavoriteResultCode.ALREADY_FAVORITED` 契约）互相印证。

### 2.4 局限与正确做法（如实说明）

用**单一账号**做写压测，必然很快撞到限流阈值 —— 这测的是"限流是否生效"，
而不是"写吞吐上限"。若要测真实写吞吐，应：

1. 按限流**维度**（用户 / IP / 参数）把压力分散到多个账号；
2. 或改用不受限流约束的管理类接口（如后台审核）另做一组对照；
3. 并在此基础上区分"应用层吞吐"与"数据库写入吞吐"（本次 DB QPS ≈ 30.9）。

## 四、可直接写进论文的结论

1. **防击穿有效**：50 并发冲击同一过期热点 key，只触发 1 次缓存重建（保护倍数 50×），
   全程 0 错误、P95 稳定在 90 ms；
2. **写接口的并发保护是双重的**：限流（429）挡住刷接口，唯一约束（4001）挡住重复写入，
   实测 10 并发下 6,887 次循环、0 异常；
3. **压测方法本身也要校准**：判断"是否被击穿"必须先用基线换算重建次数，
   否则会把"一次重建要 9 条 SQL"误读成"被击穿了 9 次"——
   这一点与单元测试中"条件构造器参数懒物化"一样，属于容易误判的工程细节。
