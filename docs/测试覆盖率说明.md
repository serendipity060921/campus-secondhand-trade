# 测试覆盖率说明（JaCoCo）

> 校园二手交易平台 · v0.17 引入 · 用数字回答"测试到底做得怎么样"

## 一、为什么要引入覆盖率

在此之前，项目的测试规模是用**用例条数**描述的（端到端 31 条、单元测试 111 条 —— 前端纯函数 76 + 后端 35），
但"条数多"不等于"覆盖广"——**有没有测到、哪里完全没测**，说不清楚。
引入 JaCoCo 后，这两个问题都有了可量化、可对比、可回归的答案。

## 二、怎么跑

```bash
cd backend
./mvnw test            # 跑测试 + 生成覆盖率 + 执行棘轮检查
# 报告位置：
#   target/site/jacoco/index.html   ← 浏览器打开，可下钻到类/方法/行
#   target/site/jacoco/jacoco.csv   ← 明细数据，可脚本汇总
```

CI 中 `./mvnw -B package` 会先执行 `test`，因此**覆盖率棘轮在 CI 里自动生效**，
报告以 `jacoco-coverage` 产物上传。

## 三、度量口径（重要，决定了数字是否有意义）

分母**排除了**实体、DTO、VO、配置与启动类：

```xml
<excludes>
  **/entity/**  **/dto/**  **/vo/**  **/config/**  **/*Application.class
</excludes>
```

原因：这些类几乎只有 getter/setter 与常量，若计入分母会把真实覆盖率"稀释"得非常低，
指标也就失去了指导意义。排除后统计的是**真正有逻辑的代码**。

| 日期 | 动作 | 整体指令覆盖率 | 变化 |

当前各包情况：

| 包 | 覆盖率 | 说明 |
| --- | --- | --- |
| `common.moderation` | **92.20%** | 内容机审（TDD：先写测试后写实现） |
| `common.result` | **69.66%** | 错误码枚举 + Result + PageResult |
| `common.cache` | **44.50%** | 缓存键规范（其余为 CacheEvictor，需要 Redis 或在测试中桩件化） |
| `common.exception` | **25.39%** | 业务异常体系（构造器透传、继承关系、动态原因拼接） |
| `service.impl` / `websocket` / `controller` | 0% | 下一步重点（见第六节） |

**这一段的论文价值**：覆盖率不是一次性数字，而是一条**可复现的提升曲线** ——
每个数据点都对应一批可查证的测试代码与一次 CI 记录，可以直接画成折线图。

其中「错误码枚举不变量」这类测试值得单独说明：它用反射遍历全部枚举，把**口头约定**变成**可执行断言**：

- 每个模块的业务码必须落在自己的千位段内（2xxx 用户 / 3xxx 商品 / 4xxx 收藏 /
  5xxx 消息 / 6xxx 订单 / 7xxx 分类 / 8xxx 管理）；
- 同一枚举内业务码不得重复（HTTP 语义码 400/401/403/404/405/429/500 例外）；
- 商品模块 3001~3010 的占用关系固定下来 —— 这条源自一次真实教训：
  接入内容机审时新增错误码，差点占用已被"图片上传失败"使用的 3008。

今后任何人新增错误码若违反约定，CI 会直接失败。

## 五、棘轮策略（只许上升）

与项目已有的"设计令牌纪律""状态与可达性检查"保持同一套哲学：

```xml
<!-- pom.xml：基线 10.12%（2026-10-15 实测），阈值设 9% —— 略低于实测值以留出日常改动余量 -->
<limit><counter>INSTRUCTION</counter><value>COVEREDRATIO</value><minimum>0.09</minimum></limit>
```

规则：**每补完一块测试，就把这个 minimum 上调一次**，覆盖率只许上升、不许回退。

## 六、下一步该测哪里（由覆盖率报告直接得出）

未覆盖指令最多的核心包（按规模排序，2026-10-15 数据）：

| 包 | 未覆盖指令 | 建议 |
| --- | --- | --- |
| `service.impl` | 10,908 | ★ 优先：订单状态流转、商品发布/上下架、内容机审接入点 |
| `websocket` | 1,693 | 会话注册表（在线状态、广播）适合单测 |
| `common.result` | 549 | 剩余为 `Result` / `PageResult` 的构造与判定方法 |
| `common.cache` | 391 | 缓存键生成（纯字符串拼接，成本极低） |
| `service`（接口层） | 374 | 随实现类测试一并覆盖 |
| `common.aspect` | 326 | 限流切面（可用独立实例 + Mock 测试） |
| `common.exception` | 432 | 其余模块异常类与全局异常处理器 |
| `controller` | 953 | 配合 MockMvc 做接口层测试 |

**建议的推进顺序**：`common.cache` 缓存键（半天）→ 订单状态机（1 天）→ 限流切面（半天）
→ 接口层 MockMvc（1 天）→ `Result`/`PageResult`（2 小时）。每完成一块，把棘轮阈值上调一次。

## 七、前端覆盖率（暂未引入，如实说明）

前端目前的单测是**纯函数级**（`tests/unit/*.mjs`，Node 直跑，共 76 条断言），
覆盖 `utils/productRules.js`、`utils/catalogue.js` 等逻辑；
组件渲染与交互由**端到端测试**（Playwright 31 条）覆盖。
若需要前端行覆盖率，可引入 `c8`（对现有 .mjs 测试零改动即可统计），
但组件级覆盖率需要引入 Vitest + 组件测试，工作量较大，暂未纳入本次范围。
