# 测试覆盖率说明（JaCoCo）

> 校园二手交易平台 · v0.17 引入 · 用数字回答"测试到底做得怎么样"

## 一、为什么要引入覆盖率

在此之前，项目的测试规模是用**用例条数**描述的（端到端 31 条、单元测试 111 条），
但"条数多"不等于"覆盖广"——**有没有测到、哪里完全没测**，说不清楚。
引入 JaCoCo 后，这两个问题都有了可量化、可对比、可回归的答案。

截至最新一轮，自动化用例总数为 **244 条**：
端到端 31 条 + 部署验证 28 条 + 单元测试 185 条（后端 109 + 前端纯函数 76）。

## 二、怎么跑

```bash
cd backend
./mvnw test            # 跑测试 + 生成覆盖率 + 执行棘轮检查
# 报告位置：
#   target/site/jacoco/index.html   ← 浏览器打开，可下钻到类/方法/行
#   target/site/jacoco/jacoco.csv   ← 明细数据，可脚本汇总
```

CI 中 `./mvnw -B package` 会先执行 `test`，因此**覆盖率棘轮在 CI 里自动生效**，
报告以 `jacoco-coverage` 产物上传。

## 三、度量口径（重要，决定了数字是否有意义）

分母**排除了**实体、DTO、VO、配置与启动类：

```xml
<excludes>
  **/entity/**  **/dto/**  **/vo/**  **/config/**  **/*Application.class
</excludes>
```

原因：这些类几乎只有 getter/setter 与常量，若计入分母会把真实覆盖率"稀释"得非常低，
指标也就失去了指导意义。排除后统计的是**真正有逻辑的代码**。

### 几组"把约定变成断言"的测试

- **错误码枚举不变量**（反射遍历 9 个枚举）：业务码必须落在本模块千位段内
  （2xxx 用户 / 3xxx 商品 / 4xxx 收藏 / 5xxx 消息 / 6xxx 订单 / 7xxx 分类 / 8xxx 管理）、
  同一枚举内不重复（HTTP 语义码 400/401/403/404/405/429/500 例外）、
  商品模块 3001~3010 占用关系固定 —— 这条源自一次真实教训：
  接入内容机审时新增错误码，差点占用已被"图片上传失败"使用的 3008。
- **缓存键规范**：参数顺序无关（否则缓存永远命中不了）、剔除空值、
  通配模式必须能匹配到它要删的具体键（否则脏缓存删不掉）。
  其中分类列表键带 `:all / :top` 后缀、必须按模式删除这一点，
  对应 v0.12 用例 C6 发现过的真实漏删问题。
- **限流切面的降级策略**：Redis 不可用时**放弃限流而不是拒绝全部请求**（可用性优先）。
  这条必须有测试守住 —— 一次不小心的改动就可能让整站被限流打死。
- **全局异常处理器**：10 个处理分支全部映射到正确的业务码
  （参数类 400 / 方法不支持 405 / 404 / 唯一键冲突 1002 / 兜底 500），
  且任何分支都**不返回 data**、都带服务端时间戳。

## 五、棘轮策略（只许上升）

与项目已有的"设计令牌纪律""状态与可达性检查"保持同一套哲学：

```xml
<!-- pom.xml：基线 13.37%（2026-10-15 实测），阈值设 12% —— 略低于实测值以留出日常改动余量 -->
<limit><counter>INSTRUCTION</counter><value>COVEREDRATIO</value><minimum>0.12</minimum></limit>
```

规则：**每补完一块测试，就把这个 minimum 上调一次**，覆盖率只许上升、不许回退。
阈值上调时按项目惯例做一次反向验证（把阈值临时调高，构建必须失败），确认门禁真的会拦人。

**建议的推进顺序**：订单状态机（1 天，收益最大）→ 会话注册表（半天）
→ 接口层 MockMvc（1 天）→ 缓存服务实现（随 service.impl 一并覆盖）。
每完成一块，把棘轮阈值上调一次。
