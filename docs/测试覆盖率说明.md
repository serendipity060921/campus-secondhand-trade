## 一、为什么要引入覆盖率

在此之前，项目的测试规模是用**用例条数**描述的，但"条数多"不等于"覆盖广"——
**有没有测到、哪里完全没测**，说不清楚。引入覆盖率工具后，这两个问题都有了可量化、
可对比、可回归的答案。

截至最新一轮，自动化用例总数为 **676 条**：

| 类别 | 条数 | 工具 |
| --- | ---: | --- |
| 端到端测试 | 31 | Playwright（Edge） |
| 部署与接口验证 | 28 | 自研 Python 套件（D1–D28） |
| 安全测试 | 52 | 自研 Python 套件（注入 / XSS / JWT / 越权 / 信息泄露 / 健壮性 / **上传校验**） |
| 后端单元测试 | 489 | JUnit 5 + Mockito + JaCoCo |
| 前端纯函数测试 | 76 | Node 直跑 + c8 |
| **合计** | **676** | |

> 📌 **v0.18 口径变更（诚实地标注在数据旁边）**：接入了 `backend/lombok.config`
> （`lombok.addLombokGeneratedAnnotation = true`），让 JaCoCo **排除 Lombok 自动生成的方法**
> （getter/setter/equals/hashCode/toString）。原因是像 `Result`/`PageResult` 这类类
> 源码只有几个字段与工厂方法，但 `@Data` 会生成十几个方法、约 180 条指令，
> 它们长期表现为"未覆盖"，把真实覆盖率压低、也让"哪块逻辑还没测"这个信号被噪声淹没。
> **手写的构造器、工厂方法与业务逻辑仍然统计**。这是一次**指标含义的修正**，
> 因此与上表历史数据不直接可比 —— 变更点已在下表标出。

## 二、怎么跑

> 📋 **逐条用例清单见 [`docs/测试用例表.md`](./测试用例表.md)**（合计 512 条，
> 由 `python tools/gen-test-case-table.py` 从各套件实测产物自动汇总；本文档讲的是覆盖率口径）。

```bash
# 后端：跑测试 + 生成覆盖率 + 执行棘轮检查
cd backend
./mvnw test
#   target/site/jacoco/index.html   ← 浏览器打开，可下钻到类/方法/行
#   target/site/jacoco/jacoco.csv   ← 明细数据，可脚本汇总

# 前端：跑纯函数单测（76 条）+ c8 覆盖率
cd frontend
pnpm test:unit
pnpm test:coverage
```

CI 中 `./mvnw -B package` 会先执行 `test`，因此**后端覆盖率棘轮在 CI 里自动生效**；
前端覆盖率与依赖审计也已接入 CI 的 frontend job（见 `.github/workflows/ci.yml`）。

## 三、度量口径（重要，决定了数字是否有意义）

后端分母**排除了**实体、DTO、VO、配置与启动类：

```xml
<excludes>
  **/entity/**  **/dto/**  **/vo/**  **/config/**  **/*Application.class
</excludes>
```

原因：这些类几乎只有 getter/setter 与常量，若计入分母会把真实覆盖率"稀释"得非常低，
指标也就失去了指导意义。排除后统计的是**真正有逻辑的代码**。

## 五、几组"把约定变成断言"的测试

- **错误码枚举不变量**（反射遍历 9 个枚举）：业务码必须落在本模块千位段内、
  同一枚举内不重复（HTTP 语义码例外）、商品模块 3001~3010 占用关系固定 ——
  源自接入内容机审时差点占用已被"图片上传失败"使用的 3008。
- **缓存键规范**：参数顺序无关、剔除空值、通配模式必须能匹配到它要删的具体键；
  分类列表键带 `:all / :top` 后缀必须按模式删除（v0.12 用例 C6 发现过真实漏删）。
- **限流切面的降级策略**：Redis 不可用时**放弃限流而不是拒绝全部请求**（可用性优先）。
- **全局异常处理器**：10 个分支映射到正确业务码，且都不返回 data、都带时间戳。
- **订单状态机**：★ 防一物多卖 —— 条件更新影响 0 行时必须抛异常且**不落订单、不清缓存**；
  完成 → 商品已售出 + 双方信用分 +1；取消 → 商品回到在售且条件是"当前正处于交易中"；
  非买卖双方一律 6004；行为埋点失败不得影响下单。
- **WebSocket 会话注册表**：多端在线语义（只有全部断开才算离线）、
  离线后不残留 userId、定向推送跳过已关闭连接、单个坏连接不影响整批推送、
  并发上下线后统计仍然自洽。
- **★ 商品模块的缓存纪律**（三条用真实缺陷换来的规则，现已全部写成断言）：
  ① **待审核商品绝不写公共缓存** —— 缓存 Key 只按商品 ID 划分、不含访问者身份，
  而"待审核是否可见"取决于身份（卖家本人 / 管理员可见，其他人按不存在处理）；
  ② **空值缓存只用于"商品确实不存在"** —— 若把"对某访问者不可见"也缓存成空值，
  卖家与管理员随后会被误判为 3001；
  ③ **行为埋点必须同时挂在缓存命中路径上** —— 否则热门商品的重复浏览学不到，
  推荐数据被缓存"截断"（v0.11 用例 R17）。
  另外还覆盖了**防击穿的完整降级链**：抢到锁 → 回源并写缓存；没抢到 → 短暂等待重读；
  仍没有 → 直接查库且**不写缓存**，绝不阻塞用户。

### 单测中的五个真实工程细节（值得写进论文）

1. **MyBatis-Plus 的 Lambda 条件构造器需要实体元数据**：`LambdaUpdateWrapper` 把
   `Product::getStatus` 解析成列名时依赖 `TableInfo`，而该元数据通常由 MyBatis 启动时注册。
   纯单元测试没有 Spring/MyBatis 环境，因此在 `@BeforeAll` 中显式初始化，
   否则被测代码里构造条件更新就会抛异常（本次实测：20 个用例因此报错）。
2. **条件构造器的参数是"懒物化"的**：`set(...)` 的参数会立即进入 `paramNameValuePairs`，
   而 `eq(...)` 等 where 条件的参数要等取一次 `getSqlSegment()` 才会写入。
   断言 where 条件时若忽略这一点，会得到"条件不存在"的假象。
3. **Mockito 与基本类型**：对 `void record(Long, Long, int)` 这类方法打桩时，
   若第三个参数误用 `any()`（返回 null），会在拆箱时抛 NPE，
   并且**污染 Mockito 内部状态**，导致同一轮里其他看似无关的用例连锁失败。
   正确写法是 `anyInt()`。
4. **mock 的 `save()` 不会回填自增主键**：被测代码插入后要拿 `product.getId()` 做缓存失效，
   而 mock 不会像 MyBatis-Plus 那样回填主键，于是断言会看到 `productChanged(null)`。
   解法是用 `doAnswer` 在 save 时把 id 塞回实体（本次实测：1 条用例因此失败）。
5. **`IService` 的单参重载会让 `any()` 歧义**：`list(Wrapper)` 与 `list(IPage)` 同时存在，
   写 `list(any())` 会报"引用不明确"，需显式写成 `list((Wrapper<T>) any())`。
6. **不要在 `thenReturn(...)` 的参数里创建并打桩另一个 mock**：Mockito 会抛
   `UnfinishedStubbingException`（"在 thenReturn 完成前又去桩另一个 mock"）。
   本次实测 7 个用例因此集体报错。解法：要么把内层打桩提前到独立语句，
   要么（更好）**用真实对象代替 mock** —— 例如把 `Claims` 换成 jjwt 的 `DefaultClaims`，
   一次修好全部调用点。

## 六、棘轮策略（只许上升）

与项目已有的"设计令牌纪律""状态与可达性检查"保持同一套哲学：

```xml
<!-- pom.xml：基线 48.40%（2026-10-16 实测，已按 v0.18 口径排除 Lombok 生成代码），阈值设 47% -->
<limit><counter>INSTRUCTION</counter><value>COVEREDRATIO</value><minimum>0.47</minimum></limit>
```

规则：**每补完一块测试，就把这个 minimum 上调一次**，覆盖率只许上升、不许回退。
阈值上调时按项目惯例做一次反向验证（把阈值临时调高，构建必须失败），确认门禁真的会拦人。
