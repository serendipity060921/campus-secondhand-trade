# 测试覆盖率说明（JaCoCo）

> 校园二手交易平台 · v0.17 引入 · 用数字回答"测试到底做得怎么样"

## 一、为什么要引入覆盖率

在此之前，项目的测试规模是用**用例条数**描述的，但"条数多"不等于"覆盖广"——
**有没有测到、哪里完全没测**，说不清楚。引入 JaCoCo 后，这两个问题都有了可量化、
可对比、可回归的答案。

截至最新一轮，自动化用例总数为 **278 条**：
端到端 31 条 + 部署验证 28 条 + 单元测试 219 条（后端 143 + 前端纯函数 76）。

## 二、怎么跑

```bash
cd backend
./mvnw test            # 跑测试 + 生成覆盖率 + 执行棘轮检查
# 报告位置：
#   target/site/jacoco/index.html   ← 浏览器打开，可下钻到类/方法/行
#   target/site/jacoco/jacoco.csv   ← 明细数据，可脚本汇总
```

CI 中 `./mvnw -B package` 会先执行 `test`，因此**覆盖率棘轮在 CI 里自动生效**，
报告以 `jacoco-coverage` 产物上传。

## 三、度量口径（重要，决定了数字是否有意义）

分母**排除了**实体、DTO、VO、配置与启动类：

```xml
<excludes>
  **/entity/**  **/dto/**  **/vo/**  **/config/**  **/*Application.class
</excludes>
```

原因：这些类几乎只有 getter/setter 与常量，若计入分母会把真实覆盖率"稀释"得非常低，
指标也就失去了指导意义。排除后统计的是**真正有逻辑的代码**。

## 五、几组"把约定变成断言"的测试

- **错误码枚举不变量**（反射遍历 9 个枚举）：业务码必须落在本模块千位段内、
  同一枚举内不重复（HTTP 语义码例外）、商品模块 3001~3010 占用关系固定 ——
  源自接入内容机审时差点占用已被"图片上传失败"使用的 3008。
- **缓存键规范**：参数顺序无关、剔除空值、通配模式必须能匹配到它要删的具体键；
  分类列表键带 `:all / :top` 后缀必须按模式删除（v0.12 用例 C6 发现过真实漏删）。
- **限流切面的降级策略**：Redis 不可用时**放弃限流而不是拒绝全部请求**（可用性优先）。
- **全局异常处理器**：10 个分支映射到正确业务码，且都不返回 data、都带时间戳。
- **订单状态机**：★ 防一物多卖 —— 靠"条件更新"把商品从在售改为交易中，
  影响行数为 0 时必须抛异常且**不落订单、不清缓存**；完成 → 商品已售出 + 双方信用分 +1；
  取消 → 商品回到在售且条件是"当前正处于交易中"；非买卖双方一律 6004；
  行为埋点失败不得影响下单。

### 单测中的两个真实工程细节（值得写进论文）

1. **MyBatis-Plus 的 Lambda 条件构造器需要实体元数据**：`LambdaUpdateWrapper` 把
   `Product::getStatus` 解析成列名时依赖 `TableInfo`，而该元数据通常由 MyBatis 启动时注册。
   纯单元测试没有 Spring/MyBatis 环境，因此在 `@BeforeAll` 中显式初始化，
   否则被测代码里构造条件更新就会抛异常（本次实测：20 个用例因此报错）。
2. **条件构造器的参数是"懒物化"的**：`set(...)` 的参数会立即进入 `paramNameValuePairs`，
   而 `eq(...)` 等 where 条件的参数要等取一次 `getSqlSegment()` 才会写入。
   断言 where 条件时若忽略这一点，会得到"条件不存在"的假象。

## 六、棘轮策略（只许上升）

与项目已有的"设计令牌纪律""状态与可达性检查"保持同一套哲学：

```xml
<!-- pom.xml：基线 19.02%（2026-10-15 实测），阈值设 18% -->
<limit><counter>INSTRUCTION</counter><value>COVEREDRATIO</value><minimum>0.18</minimum></limit>
```

规则：**每补完一块测试，就把这个 minimum 上调一次**，覆盖率只许上升、不许回退。
阈值上调时按项目惯例做一次反向验证（把阈值临时调高，构建必须失败），确认门禁真的会拦人。
