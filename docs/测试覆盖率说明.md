# 测试覆盖率说明（JaCoCo）

> 校园二手交易平台 · v0.17 引入 · 用数字回答"测试到底做得怎么样"

## 一、为什么要引入覆盖率

在此之前，项目的测试规模是用**用例条数**描述的（端到端 31 条、单元测试 76 条），
但"条数多"不等于"覆盖广"——**有没有测到、哪里完全没测**，说不清楚。
引入 JaCoCo 后，这两个问题都有了可量化、可对比、可回归的答案。

## 二、怎么跑

```bash
cd backend
./mvnw test            # 跑测试 + 生成覆盖率 + 执行棘轮检查
# 报告位置：
#   target/site/jacoco/index.html   ← 浏览器打开，可下钻到类/方法/行
#   target/site/jacoco/jacoco.csv   ← 明细数据，可脚本汇总
```

CI 中 `./mvnw -B package` 会先执行 `test`，因此**覆盖率棘轮在 CI 里自动生效**，
报告以 `jacoco-coverage` 产物上传。

## 三、度量口径（重要，决定了数字是否有意义）

分母**排除了**实体、DTO、VO、配置与启动类：

```xml
<excludes>
  **/entity/**  **/dto/**  **/vo/**  **/config/**  **/*Application.class
</excludes>
```

原因：这些类几乎只有 getter/setter 与常量，若计入分母会把真实覆盖率"稀释"得非常低，
指标也就失去了指导意义。排除后统计的是**真正有逻辑的代码**。

## 四、当前基线（2026-10-09 实测）

| 指标 | 数值 |
| --- | --- |
| 整体指令覆盖率 | **3.38%**（603 / 17,851） |
| 整体分支覆盖率 | **3.07%**（50 / 1,627） |
| 统计类数 | 85（已排除实体/DTO/VO/配置） |
| ★ 内容机审模块 `common.moderation` | **92.20%**（603 / 654） |

**怎么解读这个"3.38%"**：它是**起点**，不是结论。
项目目前只有 1 个后端测试类（内容机审，TDD 产出），因此整体值必然偏低；
值得注意的是 —— **被 TDD 覆盖的那个模块达到了 92.2%**，这恰好说明
"先写测试"的方法在这个项目里是**可复制、能出成果**的。

## 五、棘轮策略（只许上升）

与项目已有的"设计令牌纪律""状态与可达性检查"保持同一套哲学：

```xml
<!-- pom.xml：当前最低要求 1%，基线 3.38% → 阈值刻意低于实测值，留出改进空间 -->
<limit><counter>INSTRUCTION</counter><value>COVEREDRATIO</value><minimum>0.01</minimum></limit>
```

规则：**每补完一块测试，就把这个 minimum 上调一次**，覆盖率只许上升、不许回退。
（阈值取 1% 而非直接锁 3%，是为了让日常小改动不至于误伤 CI；往下一次提高时直接改成实测值即可。）

## 六、下一步该测哪里（由覆盖率报告直接得出）

未覆盖指令最多的核心包（按规模排序）：

| 包 | 未覆盖指令 | 建议 |
| --- | --- | --- |
| `service.impl` | 10,896 | ★ 优先：订单状态流转、商品发布/上下架等**纯逻辑**可先抽出来单测 |
| `websocket` | 1,693 | 会话注册表（在线状态、广播）适合单测 |
| `common.result` / `common.exception` | 1,848 | 错误码与异常工厂，成本极低、收益明确 |
| `controller` | 953 | 配合 MockMvc 做接口层测试 |
| `common.cache` / `common.aspect` | 717 | 缓存键生成、限流切面（可用反射/独立实例测试） |

**建议的推进顺序**：错误码与异常（半天）→ 订单状态机（1 天）→ 缓存键与限流（半天）
→ 接口层 MockMvc（1 天）。每完成一块，把棘轮阈值上调一次。

## 七、前端覆盖率（暂未引入，如实说明）

前端目前的单测是**纯函数级**（`tests/unit/*.mjs`，Node 直跑，共 76 条断言），
覆盖 `utils/productRules.js`、`utils/catalogue.js` 等逻辑；

但组件级覆盖率需要引入 Vitest + 组件测试，工作量较大，暂未纳入本次范围。
