1. 项目简介 · 2 分钟（0:00–2:00）

开场（20 秒）

我的题目是《AI 辅助下的校园二手交易平台设计与实现》。一句话：面向本校学生的二手教材与闲置交易平台，解决三件事——校内可信、当面交易、信息不发散。

讲什么（60 秒，只讲四句）

  1. 技术栈：Spring Boot 3.2 + MyBatis-Plus + MySQL 8 + Redis + WebSocket / Vue 3 + Vite + Element Plus
  2. 业务闭环：注册登录 → 发布（机审三态分流）→ 浏览搜索 → 私信 → 下单 → 状态机流转 → 双向评价 + 信用分
  3. 当前进度：需求 28 条用户故事全部实现；941 条自动化用例；后端覆盖率 85.94%（门禁 83%）；CI 五个 job 全绿
  4. 论文/材料：需求规格 560 行、用户故事 28 条（105 条验收标准）、缺陷日志 19 条、截图证据 83 张

收尾（20 秒，转到演示）

下面用 8 分钟走一遍一笔真实交易的全流程——从买家下单，到卖家交付，到双方评价。

2. 系统现场演示 · 8 分钟（2:00–10:00）

三个窗口：A = 无痕（stu_demo，买家）、B = Chrome（admin，卖家+管理员）
每步都有一句"要讲的话"，照着说就行。

2.1 首页（0:00–0:40）

  • 动作：A 窗口停在首页
  • 说：这是首页，8 段分类色带按在售量着色；卡片上带分类编号（如 G4-012）和成色，方便当面找货。

2.2 搜索与筛选（0:40–1:20）

  • 动作：搜索框输入 教材 → 回车；再点左侧一个分类
  • 说：支持关键词 + 分类 + 价格区间 + 排序；搜索无结果时给空态 + 建议，不是白屏。

2.3 商品详情（1:20–1:50）

  • 动作：点开一件商品详情
  • 说：详情页有卖家信息、相关推荐、以及交易评价区（现在还没有评价，所以是空态——稍后我会回来让它长出口碑）。

2.4 买家下单（1:50–2:40）

  • 动作：A 窗口 → 点「立即购买」→ 确认
  • 说：下单会锁定商品，防止一物多卖（并发下靠唯一约束 + 事务兜底）；商品状态从「在售」变「交易中」。

2.5 卖家推进：标记待交付 → 确认已交付（2:40–3:30）

  • 动作：切到 B 窗口（admin）→「我卖出的」→ 打开刚那笔订单
  1. 点「标记可交付」→ 状态变「待交付」
  2. 再点「确认已交付」→ 状态变「待收货」
  • 说：订单状态机 6 个状态：待交易 →(卖家)待交付 →(卖家)待收货 →(买家)已完成；

1/2 阶段可退款回在售，0 阶段可取消。

按钮由状态机推导——买家在待交易阶段只能取消，看不到"确认完成"；

卖家也不能替买家确认收货（这两种越权在接口层会返回 6004/6005）。

2.6 买家确认收货（3:30–4:10）

  • 动作：切回 A →「我买到的」→ 刷新 → 此时才出现「确认收货」→ 点它
  • 说：买家确认收货后订单才变「已完成」，商品自动变「已售出」，双方信用分 +1，

并开启"双方互评"入口。

（这里特意强调：只有买家能确认完成 —— 上一版这里是个漏洞，买家能跳过卖家交付，已修，见 BUG-22）

2.7 双向评价（4:10–4:50）

  • 动作：A 窗口 →「评价这笔交易」→ 选 5 星 + 标签 + 勾选匿名→ 提交
  • 说：只有已完成订单的双方能评、每单每人一次（唯一索引兜底）；匿名只隐藏展示层，后台仍可追溯；评分联动信用分。
  • 动作：再打开该商品详情 → 滚动到评价区
  • 说：详情页立刻有平均分、好评率、星级分布——这就是口碑。

2.8 管理后台（4:50–5:45）

  • 动作：切到 B 窗口 → 后台商品审核 → 那件待审核商品 →「通过」（或「驳回」并填理由）
  • 说：发布时先过机审：命中违禁词直接拒绝、命中可疑（留联系方式/价格异常）转人工；这里是人工第 2 层。
  • 动作：点「用户管理」→ 禁用/解禁一个用户；再点「数据看板」
  • 说：看板有用户/商品/订单/举报趋势；所有管理操作都写审计日志，可追溯。

2.9 私信与已读（5:45–6:25）

  • 动作：A 窗口给 admin 发一条消息；B 窗口打开消息页查看 → 回一条
  • 说：WebSocket 实时推送，已读回执双向同步；断线自动降级为轮询兜底。

2.10 质量数据（6:25–7:20）

  • 动作：切到浏览器打开 功能故事28条场景与截图.html
  • 说：这是我最想给老师看的一页——28 条功能故事，每条一个浏览器场景 + 至少一张截图，全部由 Playwright 真点出来的；下面是 941 条用例分布与 85.94% 覆盖率。

2.11 收尾（7:20–8:00）

  • 动作：展示 GitHub Actions 五个 job 全绿截图
  • 说：单元测试 708 / 端到端 31 / 部署验证 28 / 安全 52 / 前端 91，每一个提交都会跑；覆盖率掉到 83% 以下会直接红。

3. AI 开发经验 · 3 分钟（10:00–13:00）

只讲四个真实故事，每个 40 秒，都带数字。

故事 1：TDD 不是口号，是让我发现自己读错了需求（50 秒）

订单状态机我先写了 41 条测试，一跑——红了 24 条。红的原因不是我实现错了，而是我把需求读错了两次：
① 我以为"确认收货只能买家"，但用户故事写的是"买卖双方都可完成"；
② 我以为"待交易不能直接完成"，但 AC 里明确保留了"一步完成"的快捷路径。
→ 测试先出错的好处：它把"我以为"变成"文档说的"，逼我改规则而不是改需求。

故事 2：AI 能写代码，但排障需要"可观测性"（50 秒）

CI 连续 6 轮红，日志读不到。我一步步加"失败注解"、把失败步骤拆细，最后靠注解里的 exit 127 定位到：
两个 job 缺 working-directory: backend，./mvnw 在仓库根执行 → 命令找不到。
→ 教训：看不见的地方不能靠猜，要先造观测手段。

故事 3：把"检查"工具化，才不会被自己骗（40 秒）

我写脚本把 66 个业务错误码 + 12 个状态取值全抽出来，逐条问"用户故事里有对应描述吗"；
又写脚本扫全仓库文档，抓出 5 处真矛盾（例如文档说"发布后待审核"，代码实测是直接上架）。
→ AI 写文档很快，但文档之间的一致性必须机器查。

故事 4（新增，40 秒）：需求文档里的 AC 也可能写错

订单完成流程我"照 AC 实现"了——买家在待交易就能点确认完成。同学一句"买家怎么能不等卖家交付"，
我才发现那条 AC 本身不符合交易常识。改的时候连带改了状态机、41 条单测、13 条界面用例和两处文档。
→ 教训："照文档实现"不是免责理由，AC 与业务冲突时要回到需求方确认。

故事 5：AI 也会犯错，所以我改了工具默认值（40 秒）

最惨的一次：我为跑测试反复执行"复位脚本"，把同学真实发布的商品删了两次。
之后我做了三件事：默认库改成测试库、检测到非演示数据就拒绝执行、每次清库前自动备份。
→ AI 协作的关键不是"它不犯错"，而是"错了能被发现、并且下次犯不了"。

4. 提问预案 · 2 分钟（13:00–15:00）

可能会被问建议回答（30 秒内）
数据量多大？能撑并发吗？演示库 4 用户 / 18 商品；压测做过缓存与限流（Redis 缓存商品列表与详情，登录 20 次/分限流），瓶颈在 DB 写入，可加读写分离
为什么不用 Elasticsearch？当前数据量下 MySQL 全文/前缀索引足够；要上是数据量或模糊匹配需求变化时，属于"可扩展点"而非当前必需
安全性怎么保证？JWT + 拦截器统一鉴权（@LoginRequired）；越权有 52 条安全用例（匿名 401 / 普通用户 403 / 只能操作自己的资源）；图片上传限类型与大小
机审是关键词匹配，准确率如何？现在是"违禁词 + 可疑规则 + 联系方式正则"三层，故意做得保守：可疑就转人工，不直接拒；后续可接第三方内容安全 API
买家能跳过卖家直接完成吗？不能（v0.19 已修）：必须 卖家标记可交付 → 卖家确认已交付 → 买家确认收货；越权返回 6004/6005
信用分怎么算？4~5 星 +1、3 星不变、1~2 星 −1，夹在 [0,150]；每单只变一次，SQL 原子更新
一个人做的还是团队？独立完成；AI 承担编码与排障的大部分重复劳动，需求/验收/取舍由我定
AI 生成代码的可信度？靠三件事兜底：测试（941 条）、CI 门禁（覆盖率阈值 + 用例数棘轮）、人工审阅（我逐条核对业务规则）
毕设做 TDD 现实吗？现实但代价明显：写测试的时间超过写实现；收益是重构不慌、答辩有硬证据（红→绿的过程可复现）
下一步计划？补端到端进 CI、组件测试扩展到更多页面、论文排版与中期材料整理
