# 越权矩阵实测（v0.18 / 第4批-⑬）

> 一句话结论：**29 个受保护接口 × 4 类 caller 身份，共 43 项检查，0 项失败**；
> 同时发现一处**信息泄露层面的设计权衡**（越权用业务码而非统一返回 404，攻击者可据此枚举资源是否存在），已列为改进项而非缺陷。

- 实测目标：`http://127.0.0.1:8080`（prod profile）
- 实测时间：2026-10-16
- 工具：`tools/check-authz-matrix.py`（零第三方依赖，已落盘原始数据 `docs/test-evidence/越权矩阵-数据.json`）
- 复现：`python tools/check-authz-matrix.py --json docs/test-evidence/越权矩阵-数据.json`

---

## 一、为什么还要做「矩阵」，而不是只留 S 用例

安全套件里的 S 用例是**单点验证**：`S26 普通用户访问管理端 → 403`。
它证明"这一个接口"被拦住了，但不能回答三个问题：

1. **有没有哪个受保护接口被漏掉了**（新增接口忘了加 `@LoginRequired`）；
2. **同一类风险在别的资源上是否也成立**（订单越权被拦了，商品的越权呢？）；
3. **"我的"类接口会不会把别人的数据混进结果**（这是比 403 更隐蔽的一类越权）。

矩阵化就是对这三个问题的系统性回答：把「接口 × 身份」铺开，逐格实测。

## 二、方法

### 2.1 四类探针

| 探针 | 问的问题 | 期望 |
| --- | --- | --- |
| `AUTH` | 不带 Token 能访问吗？ | 全部 `401` |
| `ROLE` | 普通用户能打管理员接口吗？ | 全部 `403` |
| `OWNERSHIP` | 非属主能读写他人资源吗？ | 必须被拒（`code ≠ 200`） |
| `SELF_SCOPE` | 「我的」列表里会混入他人资源吗？ | 泄漏条数 = 0 |

### 2.2 四个身份

| 身份 | 账号 | 用途 |
| --- | --- | --- |
| 匿名 | — | 验证鉴权入口 |
| A（属主） | `stu_test01` | 资源的合法拥有者 |
| B（非属主） | `stu_demo` | 越权尝试者 |
| 管理员 | `admin` | 验证管理员专属接口 |

### 2.3 三条设计原则（避免"为了好看而测试"）

1. **不污染数据**：写接口只打"应被拒绝"的方向（拒绝即无副作用）；"改自己资料"用当前值回写（幂等）。
   —— 实测后 `seed-demo-data.py --verify` 仍通过（`user 4 / product 17 / favorite 4 / orders 4 / message 9`）。
2. **不硬编码资源 ID**：订单号、商品号全部先通过 API 自行发现；发现不到就标记「无数据」，而不是假装通过。
3. **失败即失败**：任何一格不符合预期，脚本退出码为 1，可直接接 CI。

## 三、结果

### 3.1 匿名访问 29 个受保护接口 → **全部 401**

覆盖：订单 5（创建/改状态/我买到的/我卖出的/详情）、私信 7（未读数/在线/发送/会话列表/记录/已读/对象信息）、
收藏 3（收藏操作/我的收藏/是否已收藏）、商品 4（发布/上传/我的商品/状态变更）、
举报 2（提交/我的举报）、用户 5（信息/退出/资料/改资料/上传头像）、管理端 3（看板/新增分类/修改分类）。

> 结果：**29 / 29 通过**。没有任何受保护接口在匿名状态下返回业务数据。

### 3.2 管理员专属接口 × 普通用户 → **403**

| 接口 | A（普通用户） | B（普通用户） | admin |
| --- | ---: | ---: | ---: |
| `GET /api/admin/dashboard` | 403 | 403 | 200 |
| `POST /api/category/add` | 403 | 403 | 200（未实际调用，仅确认拦截点） |
| `PUT /api/category/update` | 403 | 403 | 200（同上） |

> 说明：管理端接口用 `@LoginRequired(admin = true)`，拦截器在进入控制器之前就拒绝，
> 因此**不存在"控制器里忘了判角色"的可能**。

### 3.3 越权尝试（非属主 B 访问 A 的资源）

| 尝试 | 实际返回 | 期望 | 判定 |
| --- | --- | --- | :---: |
| B 读 A 的订单详情 `GET /api/order/{A的单号}` | `6004 无权查看或操作该订单` | 拒绝 | ✅ |
| B 把 A 的订单改成已完成 `PUT /api/order/status` | `6004` | 拒绝 | ✅ |
| B 下架 A 的商品 `PUT /api/product/status` | `3002 无权操作他人发布的商品` | 拒绝 | ✅ |
| B 拉取与 A 的会话历史（试图读 A 与他人的聊天） | `200`，但只返回 B 参与的会话 | 只能读自己参与的 | ✅ |
| A 读自己的订单详情（属主反向验证） | `200` | 200 | ✅ |

> 「属主反向验证」这一列很关键：如果属主也读不到，说明是被"一律拒绝"掩盖了功能缺陷，
> 那 403 就不是安全，而是坏了。矩阵必须两边都测。

### 3.4 「我的」类列表不泄漏他人资源

| 接口 | B 的返回条数 | 其中属于 A 的资源条数 | 判定 |
| --- | ---: | ---: | :---: |
| `GET /api/order/buyList` | 2 | 0 | ✅ |
| `GET /api/order/sellList` | 0 | 0 | ✅ |
| `GET /api/product/mine` | 2 | 0 | ✅ |

> 这类越权比 403 更隐蔽：接口本身"允许访问"，但结果集里混入了别人的数据。
> 因此判定方式不是看状态码，而是**比对两边的资源 ID 集合是否相交**。

## 四、★ 发现的一处设计权衡（已列为改进项，不是缺陷）

越权被拒绝时，接口返回的是**业务码**而不是统一的状态码：

| 场景 | 返回 | 含义 |
| --- | --- | --- |
| 订单**不存在** | `6003 订单不存在` | 资源不存在 |
| 订单**存在但无权** | `6004 无权查看或操作该订单` | 资源存在，只是不给你 |
| 商品**不存在** | `3001 商品不存在或已被删除` | 资源不存在 |
| 商品**存在但非本人** | `3002 无权操作他人发布的商品` | 资源存在，只是不是你的 |

**好处**：用户能看到"为什么不行"，前端可以据此给不同引导（去逛逛 / 联系客服）。

**代价**：攻击者可以**枚举资源是否存在** —— 遍历订单号时，`6003` 与 `6004` 的差异
本身就泄漏了"这个订单号有没有被占用"。对校园二手平台这种**订单号连号**的场景，
这属于较低风险但确实存在的**信息泄露面**。

**建议（未实施，留作后续）**：对外统一返回「资源不存在」（404 / 6003），
内部日志与审计里再区分 `无权`。本项目的取舍是"用户体验优先"，因此**保留现状并明确记录**，
而不是悄悄当成没看见。

## 五、尚未覆盖的越权面（如实列出）

| 面 | 状态 | 说明 |
| --- | --- | --- |
| **WebSocket 通道** | ❌ 未做矩阵 | REST 与 WS 是两条发送路径，WS 入站消息的身份校验目前只有单测覆盖（`WsInboundMessageTest`），没有端到端越权探测 |
| **文件访问** | 🟡 部分覆盖 | `ImageTypeValidator` 的路径穿越单测已覆盖（`../../evil.png` 落盘仍在上传根目录内），但没有"用别人的 URL 直接访问"的越权测试（静态资源本就公开，属设计如此） |
| **时间窗口竞争** | ❌ 未做 | 例如"取消订单"与"确认完成"并发时的状态竞争，属并发一致性而非越权，留给 ⑭ 写路径压测 |
| **管理端批量导出** | — | 项目没有导出接口，不涉及 |

## 六、与其它测试套件的关系

```
安全套件（52 条 S 用例）  →  单点：注入 / XSS / JWT 伪造 / 限流 / 信息泄露 / 上传校验
本矩阵（43 项）            →  系统：接口 × 身份 的横切覆盖
接口层单测（65 条）        →  接线：身份只能取自上下文、未登录不落库
服务层单测（75 条）        →  语义：谁的资源谁才能改，状态机是否严格
```

四层叠加才构成"越权"这件事的完整证据链：**能拦（矩阵）、拦得对（单测）、拦完数据还在（不变量校验）**。
