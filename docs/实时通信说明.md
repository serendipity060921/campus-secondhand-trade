# 校园二手交易平台 · 实时通信设计说明（v0.14）

> 本文是论文"实时通信 / 系统优化"章节的素材：说明为什么把轮询改成 WebSocket、
> 连接如何鉴权、消息协议怎么设计、断线重连与心跳怎么做、在线状态与离线消息如何处理，
> 以及开发过程中发现的、具有普遍意义的两个坑。

---

## 一、为什么要从轮询改成 WebSocket

v0.07 的私信是"客户端每 5 秒拉一次"实现的，属于典型的**短轮询**：

| 问题 | 具体表现 |
| --- | --- |
| 延迟 | 消息最坏要等 5 秒才出现，聊天体验像"发邮件" |
| 无效请求 | 没有新消息时也在请求，20 个在线用户闲置时每分钟产生 240 次空查询 |
| 服务器压力 | 每次轮询都是一次完整 HTTP 请求（建连、鉴权、查库、序列化） |
| 浪费带宽 | 重复传输相同的消息列表 |

改成 **WebSocket** 后：连接只建立一次（HTTP Upgrade），之后消息由服务端**主动推送**，
没有新消息时连接静默（只保留 25 秒一次的心跳）。

| 指标 | 轮询（v0.07） | WebSocket（v0.14） |
| --- | --- | --- |
| 消息到达延迟 | 0 ~ 5 秒 | 通常 < 100 毫秒 |
| 空闲时的请求量 | 每客户端 12 次/分钟 | 每客户端 2.4 次/分钟（心跳） |
| 消息传输 | 每次拉取整页历史 | 只推新增的那一条 |

> 权衡说明：WebSocket 带来的是**连接状态管理**的复杂度（鉴权、心跳、重连、多端、离线）。
> 因此本项目保留了"WebSocket 优先、REST 兜底"的双通道设计 —— 实时性由 WebSocket 提供，
> 可靠性由 REST 保证（见第四节）。

## 二、连接与鉴权

```
客户端                                       服务端
  │  ws://host/ws/chat?token=<JWT>             │
  ├───────────── HTTP Upgrade ────────────────►│
  │                                            │ ChatHandshakeInterceptor.beforeHandshake
  │                                            │   ① 解析 token（签名/有效期）
  │                                            │   ② 查 Redis 黑名单（v0.12）
  │                                            │   ③ 查用户是否存在、是否被禁用
  │                                            │   ④ 合法 → 把 userId 放进会话属性
  │◄──────────── 101 Switching Protocols ──────┤
  │◄──────────── welcome（userId + 未读总数）───┤
  │                                            │ ChatSessionRegistry.register(userId, session)
  │                                            │ OnlineStatusService.heartbeat(userId)
  │                                            │ ChatPushService.pushOnline(userId, true)
```

**为什么 Token 放在 URL 参数里？** 浏览器原生 `WebSocket` 构造函数不支持自定义请求头，
无法像 axios 那样带 `Authorization: Bearer xxx`；放在查询参数是业界通行做法。
代偿性安全措施：

1. 握手阶段就完成全部校验，不合法直接返回 **401/403**（不是"先连上再判断"）；
2. Token 只在握手时用一次，之后会话里只保留 `userId`，后续逻辑不再传递 Token；
3. 已退出登录（Redis 黑名单）与被禁用的账号都建立不了连接。

## 三、消息协议

用一个"信封 + type"的 JSON 协议（而不是 STOMP，因为本项目只有三种业务消息，
自定义协议代码更少、前端解析更直观）：

**客户端 → 服务端**

| type | 字段 | 说明 |
| --- | --- | --- |
| `chat` | `toUserId`、`content`、`productId?` | 发送私信 |
| `read` | `peerId` 或 `messageIds` | 标记已读 |
| `ping` | — | 心跳（25 秒一次） |
| `queryOnline` | `userIds[]` | 批量查询在线状态 |

**服务端 → 客户端**

| type | data | 说明 |
| --- | --- | --- |
| `welcome` | `{userId, unreadTotal}` | 连接建立时下发，用于校准未读角标 |
| `chat` | `MessageVO` | 新私信（接收方与发送方的其它标签页都会收到） |
| `read` | `{readerId, peerId}` | 对方已读回执 |
| `online` | `{userId, online}` 或数组 | 在线状态变化 |
| `pong` | — | 心跳响应 |
| `error` | `{code, message}` | 业务错误（复用全局业务状态码，如 5001） |

**设计要点**：业务规则**只写一份**。WebSocket 的 `chat`/`read` 直接调用
`MessageModuleService.send/markRead`，因此"不能给自己发消息(5001)""接收人不存在(5002)"
"只能标记自己收到的消息为已读"这些规则在 REST 与实时通道上完全一致，
不会出现"接口拦得住、WS 绕得过去"的漏洞。

## 四、可靠性设计（这是实时通信真正的难点）

| 问题 | 做法 |
| --- | --- |
| **消息丢失** | 推送**不替代落库**：`send()` 先写数据库再推送；推送失败只记 warn。对方不在线、推送失败都不影响消息持久化，下次拉历史仍能看到 |
| **断线重连** | 前端指数退避重连：1s → 2s → 4s → … 上限 30s；重连成功后服务端重新下发 welcome 校准未读 |
| **连接假死** | 客户端 25 秒发 `ping`，服务端刷新 Redis 在线时间戳；超过 90 秒无心跳视为离线（拔网线、进程被 kill 都能识别） |
| **握手失败** | 401（Token 无效/已登出）不再重连，避免无意义的死循环；网络类错误才退避重连 |
| **轮询兜底** | WebSocket 断开期间，聊天页每 15 秒轮询一次（连接正常时该函数直接 return，不产生请求），会话列表 30 秒兜底刷新 |
| **多端在线** | 注册表按"userId → 该用户的全部连接"组织（`ConcurrentHashMap` + `CopyOnWriteArraySet`）；同一账号多标签页都能收到消息，**全部关闭才算离线** |
| **并发写同一连接** | Spring 的 `WebSocketSession` 非线程安全，推送时对 session 加锁，避免并发 `sendMessage` 抛异常 |
| **限流绕过** | REST 有 `@RateLimit`，WebSocket 不走拦截器 —— 因此在 handler 内用同一套 Redis 计数器补上"30 条/分钟"，否则可以绕过限流刷消息 |
| **管理员禁用** | 禁用账号时立即 `closeUser(userId)` 断开其实时连接，否则被禁用户仍能收发消息 |
| **异常隔离** | 业务异常转成 `error` 帧返回，连接保持存活；畸形 JSON 也只回 error，不断线 |

## 五、在线状态：为什么放在 Redis

`ChatSessionRegistry`（内存）与 `OnlineStatusService`（Redis）同时存在，各司其职：

| 方案 | 作用 | 局限 |
| --- | --- | --- |
| 内存会话表 | **权威答案**：进程内判断谁有活跃连接，支持定向推送 | 只在单实例内有效 |
| Redis ZSet `campus:online:zset` | member = userId，score = 最近心跳秒级时间戳 | 多实例共享、可统计在线人数、可观察 |

选 ZSet 而不是普通 Set 的原因：**能表达"最后活跃时间"**，
于是 `ZREMRANGEBYSCORE` 可以自动淘汰过期成员（心跳停了 90 秒就是离线），
`ZCARD` 直接给出在线人数 —— 管理后台的"当前在线人数"卡片就来自这里。

## 六、前端实现要点

- **单例连接**（`utils/websocket.js`）：整个应用一条连接，页面通过
  `on('chat', fn)` 订阅事件，组件卸载时取消订阅；
- **状态集中管理**（`store/chat.js`）：连接状态、未读总数、在线映射、新消息提醒；
- **智能角标**：自己在聊天页与对方对话时，收到的消息立即标记已读且不计未读；
  不在该会话页时，未读 +1 并弹出通知（点击直接跳转到对应会话）；
- **降级透明**：`sendBySocket()` 返回 false 时自动改走 REST 接口，用户无感知；
- **可视反馈**：聊天窗口顶部显示"● 在线 / ○ 离线"，连接断开时提示"已切换为轮询"。

## 七、开发中发现并修复的问题

### 问题 1：Redis 5.0 不支持 `ZMSCORE`，批量在线查询"静默全离线"

- **现象**：WebSocket 批量查询在线状态时三个人全部返回"离线"，
  但 REST 单查同一个人却是"在线"。
- **定位**：`ZMSCORE` 是 **Redis 6.2** 才引入的命令，本项目环境是 Redis 5.0.14.1，
  调用返回 `ERR unknown command 'zmscore'`；而该异常被"降级兜底"的 catch 吞掉了，
  表现成"查不到任何人在线"。
- **修复**：改用 `ZRANGEBYSCORE`（Redis 1.0 起就有）一次取回在线窗口内的成员，再与入参求交集；
  同时给 catch 补上 `log.warn`，避免以后再出现"静默错误"。
- **启示**：① 使用中间件特性前要确认**版本兼容性**（命令、参数、默认行为）；
  ② "兜底 catch" 必须打日志，否则它会把 bug 变成"看起来正常的错误结果"，比崩溃更难查。

### 问题 2：同一秒内为同一用户签发的 JWT 完全相同

- **现象**：自动化用例里"登出后 Token 应失效"这一条，把主测试账号的 Token 也一起拉黑了，
  后续所有连接都返回 401。
- **原因**：JWT 载荷的 `iat`/`exp` 只精确到**秒**，同一秒内用相同密钥为同一用户签发，
  生成的字符串**完全一致**（同一把锁配同一把钥匙）。
- **修复**：黑名单用例改用独立临时账号（并在用例中注释说明原因）。
- **启示**：JWT 不是"每次登录都得到唯一 Token"；若业务需要"一个账号多会话互不影响"
  （例如"退出某台设备"),必须额外引入 `jti`（JWT ID）或 token 版本号。

## 九、可扩展方向

1. **消息可靠性升级**：客户端 ACK + 服务端重推队列（当前依赖"落库 + 拉历史"保证不丢）；
2. **集群化**：用 Redis Pub/Sub 或 Stream 在多个后端实例间转发推送（当前会话表在单实例内存中）；
3. **富消息**：图片、商品卡片、位置、语音（协议已是 JSON 信封，扩展 `type` 即可）；
4. **消息状态可视化**：发送中/已送达/已读三态（现在已有已读回执，可再补"送达"）；
5. **群聊/系统通知**：把在线推送能力复用到"订单状态变更提醒""管理员公告"；
6. **WebSocket 层限流升级**：从固定窗口改为令牌桶，允许短时突发。
