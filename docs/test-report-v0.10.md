## 一、测试范围与方法

| 测试部分 | 用例数 | 方法 | 工具 |
| --- | ---: | --- | --- |
| 一、主业务闭环 | 20 | 两个独立浏览器上下文分别登录账号 A（卖家）/ B（买家），按真实用户操作点击完整链路 | Playwright + 系统 Edge + 数据库断言 |
| 二、权限与越权 | 6 + 27 | 页面路由拦截实测 + 伪造 Token/身份 + 全接口 401/403 扫描 | 同上 |
| 三、各模块独立功能 | 86 + 17 | 接口调用 + 数据库断言（唯一索引、状态流转、密文、计数） | Python HTTP + mysql CLI |
| 四、异常场景 | 32 | 空参数、非法 ID、非法文件、并发竞态 | 浏览器 + 多线程并发 |

测试原则：
1. **双账号隔离**：账号 A、B 分别在两个独立浏览器上下文中登录（localStorage 互不可见），杜绝"同一账号自买自卖"导致用例失效；
2. **页面 + 数据库双重断言**：每个关键步骤既检查页面表现（提示文案、跳转、状态标签），也用 SQL 校验落库结果（状态、金额、买卖双方、密文）；
3. **越权用真身份**：越权用例使用真实的他人 Token 调用真实接口，而不是只做代码走查；
4. **并发用屏障**：两个线程用 `Barrier` 同时发请求，验证唯一索引/状态机在竞态下的正确性。

## 三、缺陷清单与修复

### BUG-01【高 · 接口越权泄漏】匿名可获取非上架商品（已修复）

| 项 | 内容 |
| --- | --- |
| 现象 | 匿名调用 `GET /api/products` 返回了待审核、已下架、交易中、已售出的商品数据 |
| 原因 | v0.03 脚手架演示接口直接分页查询，未加 `status` 条件；详情接口同理 |
| 影响 | 未公开商品信息泄漏（越权） |
| 修复 | `ProductController` 列表与详情均限定 `status = 1`，非在售按"商品不存在"处理 |
| 验证 | 用例 TC-P17 / 3A-2 / 3A-3 通过；`/dev/health` 自检看板仍正常 |

### BUG-02【中 · 未发布内容外泄】待审核商品详情对任意访问者可见（已修复）

| 项 | 内容 |
| --- | --- |
| 现象 | 用 SQL 把商品置为 `status=0`（待审核）后，匿名访问 `GET /api/product/{id}` 返回 200 |
| 原因 | 详情接口只判断"商品是否存在"，未区分状态与访问者身份；公开接口拿不到当前登录用户 |
| 修复 | ① `LoginInterceptor` 对公开接口也解析 Token（可选鉴权，异常静默忽略）；② 详情接口对待审核商品做"卖家本人 / 管理员可见"判断 |
| 验证 | 匿名 3001 / 卖家 200 / 管理员 200（三种身份实测） |

### BUG-03【低 · 前端重复请求】搜索页每次操作发送两次相同请求（已修复）

| 项 | 内容 |
| --- | --- |
| 现象 | 搜索、切换分类、翻页时同一接口出现两次请求 |
| 原因 | `handleSearch` 里既 `router.replace`（触发 `watch(route.query)` 加载）又手动调用 `loadProducts()` |
| 修复 | 统一入口 `applyAndReload()`：URL 变化交给 watcher，URL 未变化才直接查询 |
| 验证 | 搜索/筛选/翻页均只发一次请求，结果与 URL 一致 |

### BUG-04【低 · 并发错误码不友好】唯一索引冲突返回通用错误码 1002（本轮新发现，已修复）

| 项 | 内容 |
| --- | --- |
| 现象 | 同一账号两个窗口同时收藏同一商品，一个成功，另一个返回 `1002 数据已存在（违反唯一约束）`，而不是业务码 `4001 已收藏该商品` |
| 原因 | 并发下两个请求都通过了"是否已收藏"的查重，随后由数据库唯一索引 `uk_user_product` 兜底；冲突被 `GlobalExceptionHandler` 的 `DuplicateKeyException` 分支统一转成 1002 |
| 影响 | 数据正确（无脏数据、无重复记录），但提示语是技术性文案，接口语义与用户体验不清晰 |
| 修复 | ① `FavoriteModuleServiceImpl.operate` 捕获 `DuplicateKeyException` → 抛出 `FavoriteException.alreadyFavorited()`（4001）；② 同理修复 `AuthServiceImpl.register`（并发注册同一用户名 → 2001 而非 1002） |
| 验证 | 并发用例 4.4 由 `[1002, 200]` → `[200, 4001]`，数据库收藏记录数恒为 1；全量回归 161 条用例 + 14 条冒烟全部通过 |

## 五、测试结论与遗留问题

1. **功能完整**：161 条用例全部通过（通过率 100%），主业务闭环"注册→登录→发布→浏览→收藏→私聊→下单→状态变更"在真实浏览器中完整跑通，页面跳转、提示文案、数据库落库结果三者一致。
2. **权限可靠**：页面路由守卫与后端接口鉴权双重生效，越权操作全部被拒绝，未发现新的越权漏洞。
3. **异常健壮**：空参数、非法 ID、非法文件、并发竞态均给出明确提示，未出现 500 异常或脏数据。
4. **缺陷修复**：本轮修复 4 个缺陷（含 1 个并发场景新发现），修复后全量回归通过。

遗留问题（不影响本版本验收，建议后续迭代）：

- 商品审核流程未启用（发布即上架），`status=0 待审核` 分支待后台管理里程碑接入；
- 前端未做移动端响应式适配（按 ≥1366×768 设计）；
- 私信为 5 秒轮询，可升级 WebSocket；
- 未接入 Redis（验证码、限流、Token 黑名单）；
- 列表页暂未使用"锁 + 重试"的乐观锁机制，超大规模并发下仍依赖数据库唯一索引兜底。

## 七、测试数据清理说明

自动化脚本会在数据库中创建临时账号（`qa*` / `e2ea*` / `e2eb*` / `e2ec*` / `apx*`）、临时商品（标题以 `E2E` / `【测试】` / `【冒烟】` / `补充测试商品` 开头）以及对应的收藏、私信与订单。
测试完成后已按外键依赖顺序清理（message → favorite → orders → product_image → product → user），数据库恢复到演示状态：**4 个用户 / 14 件商品 / 4 张订单 / 4 条收藏 / 8 条消息 / 33 个分类**。

> 注意：`product.favorite_count` 是冗余计数字段（应用在收藏/取消时同步维护）。若直接用 SQL 删除 `favorite` 明细，需同步重算计数，否则会出现"计数与明细不一致"：
>
> ```sql
> UPDATE product p SET favorite_count = (SELECT COUNT(*) FROM favorite f WHERE f.product_id = p.id AND f.deleted = 0);
> ```
>
> 清理后已用 5 条不变式校验数据一致性（同一商品不出现两张待交易订单、待交易→商品交易中、已完成→商品已售出、无有效订单的商品在售、冗余计数与明细一致），全部通过。
