# 校园二手交易平台 · 缓存与限流设计说明（v0.12）

> 本文是论文"系统性能优化"章节的素材：说明为什么引入 Redis、缓存了什么、
> 如何保证一致性、限流如何实现，以及**压测对比数据**（含数据库减压效果）。

---

## 一、为什么要引入 Redis

v0.11 之前，所有读请求都直接打到 MySQL。系统里有三类典型的"读多写少"数据：

| 数据 | 特征 | 问题 |
| --- | --- | --- |
| 首页/搜索商品列表 | 每次刷新都查，分页 + 筛选组合多 | 高频重复查询，SQL 带 JOIN 与排序 |
| 商品详情 | 热点商品被反复打开 | 每次还要 `UPDATE view_count`，写压力被放大 |
| 分类列表 | 几乎不变，但首页/发布页/搜索页都要 | 纯重复查询 |
| 个性化推荐 | 三路打分 + 多次聚合查询，单次最"贵" | 同一用户短时间内多次刷新结果完全一样 |

引入 Redis 后：**读请求在缓存命中时完全不访问数据库**，同时把浏览量从"每次写库"改成
"Redis 去重计数 + 批量回写"，把数据库写压力也降下来。

## 二、缓存设计

### 2.1 Key 规范

统一 `前缀:业务:维度` 结构，便于 `KEYS campus:product:*` 排查与按业务批量失效：

| Key | 内容 | TTL |
| --- | --- | --- |
| `campus:product:list:{条件指纹}` | 商品列表（分页/分类/关键词/价格/排序） | 60s |
| `campus:product:detail:{id}` | 商品详情（含空值标记） | 120s |
| `campus:category:list:all\|:top` | 分类列表 | 600s |
| `campus:recommend:{userId\|anon}:{size}:{strategy}` | 推荐结果 | 300s |
| `campus:hot:{yyyyMMdd}` | 热门榜（ZSet，行为实时加分） | 3 天 |
| `campus:view:dedup:{productId}:{访问者}` | 浏览量去重标记 | 600s |
| `campus:view:counter:{productId}` | 浏览量待回写计数 | 1h |
| `campus:ratelimit:{业务}:{维度}` | 限流计数器 | 窗口时长 |
| `campus:jwt:blacklist:{sha256}` | 已退出登录的 Token 摘要 | 剩余有效期 |

### 2.2 三个经典缓存问题的应对

| 问题 | 现象 | 本系统做法 |
| --- | --- | --- |
| **缓存穿透** | 反复查询不存在的商品（如恶意 ID）→ 每次都打到数据库 | 查不到时写入**空值标记**（`__NULL__`，TTL 30s），下次直接返回 404 |
| **缓存雪崩** | 大批 Key 同一秒失效 → 请求同时压向数据库 | 所有 TTL 乘以 `[0.8, 1.2]` 的**随机抖动**；热点数据 TTL 分级（60/120/300/600s） |
| **缓存击穿** | 热点 Key 失效瞬间，大量并发线程同时回源 | 回源前用 **SET NX EX 分布式锁**，只放行一个线程查库，其他线程短暂等待后重读缓存；释放锁用 Lua 保证"值匹配才删" |

### 2.3 一致性策略（Cache-Aside + 主动失效）

```
读：查缓存 → 命中返回 → 未命中查库 → 写缓存(+TTL抖动)
写：先写库 → 再删缓存（统一走 CacheEvictor）
```

失效动作统一收敛到 `CacheEvictor` 三个方法，避免"写数据时忘了清缓存"：

| 业务动作 | 失效范围 |
| --- | --- |
| 商品发布 / 上下架 / 补图 | 该商品详情 + 列表 + 推荐 |
| 收藏 / 取消收藏 | 该商品详情 + 列表 + 推荐（详情里含 `favorite_count`） |
| 下单 / 订单状态变更 | 该商品详情 + 列表 + 推荐（商品状态联动为交易中/已售出/在售） |
| 分类新增 / 修改 | 分类列表（含 `:all` 与 `:top` 两个 Key）+ 列表 + 推荐 |
| 用户产生新行为 | **仅该用户**的推荐缓存 |

> 测试用例 C6/C7 专门验证"写操作后缓存被主动删除"，避免读到旧数据。
> 实践中的教训（已修复）：分类列表 Key 带 `:all`/`:top` 后缀，最初用精确 Key 删除会漏删，
> 改为按 `campus:category:list*` 模式删除。

### 2.4 降级容错

`CacheServiceImpl` 中所有 Redis 操作都包了 try/catch：Redis 不可用时记录 warn 日志并
**退化为直接查库**，绝不让"缓存挂了"变成"网站挂了"。压测时的 `campus.cache.enabled=false`
开关同样走这条降级路径，用于对照实验。

## 三、浏览量优化

改造前：每次打开商品详情执行 `UPDATE product SET view_count = view_count + 1`。
改造后（`ProductModuleServiceImpl.recordViewStat`）：

1. **去重**：以"登录用户 ID / 客户端 IP"为维度，用 `SET NX EX 600` 建立去重窗口，
   窗口内重复访问不计数（抑制刷新刷量）；
2. **计数**：通过去重后在 Redis `INCR`，不立即写库；
3. **批量回写**：累计达到阈值（默认 20 次）才把增量一次性写回 MySQL，把 N 次写库压成 1 次；
4. **口径一致**：缓存详情时把"数据库值 + Redis 待回写值"一起返回给前端，避免缓存期内浏览量不动。

## 四、限流设计

注解式固定窗口限流：`@RateLimit(key, limit, window, dimension)`，切面用 **Lua 脚本**保证
"自增 + 首次设置过期"原子执行（否则并发下可能出现计数器永不过期，用户被永久限流）。

| 接口 | 维度 | 阈值 | 目的 |
| --- | --- | --- | --- |
| 注册 | IP | 10 次 / 5 分钟 | 防脚本批量注册 |
| 登录 | IP | 20 次 / 分钟 | 防撞库爆破 |
| 发送私信 | 用户 | 30 次 / 分钟 | 防刷屏 |
| 发布商品 | 用户 | 10 次 / 5 分钟 | 防灌水 |
| 收藏操作 | 用户 | 60 次 / 分钟 | 阈值放宽，不影响正常使用 |

- 触发后返回业务码 **429**「操作过于频繁」（与项目统一响应体保持一致，HTTP 仍为 200）；
- **降级**：Redis 异常时放弃限流、放行请求（可用性优先于限流）；
- **本地跳过**：`campus.cache.rate-limit-skip-local=true` 时本机回环/内网地址不限流，
  避免自动化测试与压测互相干扰；线上经 Nginx 转发后取 `X-Forwarded-For` 的真实客户端 IP。
  测试用例 C13/C15 通过伪造 `X-Forwarded-For` 验证限流确实生效。

## 五、安全增强：可撤销的 JWT 会话

JWT 是无状态的，"退出登录"原本只是前端删掉 Token，被复制的 Token 在过期前仍然可用。
v0.12 增加 Redis 黑名单：

1. 退出登录时把 Token 的 **SHA-256 摘要**写入 Redis，TTL = 该 Token 的**剩余有效期**（到期自动清理）；
2. 拦截器每次鉴权后查一次黑名单，命中即返回 401；
3. 只存摘要不存原文，避免 Redis 中出现可直接使用的凭证。

测试用例 C16/C17 验证：退出后原 Token 立即失效（401），且黑名单 Key 为 64 位十六进制摘要。

## 六、压测对比实验

### 6.1 实验设置

| 项目 | 设置 |
| --- | --- |
| 工具 | 自研 Python 压测脚本（`tools/load-test.py`），线程内复用 HTTP 长连接 |
| 并发 | 20 线程 |
| 时长 | 每个场景 15 秒 |
| 场景 | 首页商品列表 / 商品详情 / 猜你喜欢(推荐) / 分类列表 |
| 对照 | `campus.cache.enabled=true`（开） vs `false`（关，同一份代码走降级路径） |
| 指标 | QPS、平均/P95/P99 延迟、错误数、**数据库实际执行语句数**（`SHOW GLOBAL STATUS LIKE 'Questions'` 差值） |
| 环境 | Windows 11 · 单机（应用、Redis、MySQL 同机）· 演示数据集 |

### 6.2 实验结果

| 场景 | 缓存关 QPS | 缓存开 QPS | 提升 | 缓存关 平均延迟 | 缓存开 平均延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首页商品列表 | 680.7 | **6507.2** | **9.6×** | 29.36 ms | **3.07 ms** |
| 商品详情 | 710.8 | **6783.8** | **9.5×** | 28.11 ms | **2.95 ms** |
| 猜你喜欢(推荐) | 553.0 | **6172.4** | **11.2×** | 36.14 ms | **3.24 ms** |
| 分类列表 | 680.3 | **6613.9** | **9.7×** | 29.38 ms | **3.02 ms** |
| **合计/平均** | **656.2** | **6518.1** | **9.9×** | **30.75 ms** | **3.07 ms** |

数据库压力对比：

| 指标 | 缓存关 | 缓存开 | 变化 |
| --- | ---: | ---: | ---: |
| 总请求数（4 场景 × 15s） | 39,311 | 390,175 | +892% |
| 数据库执行语句数 | 139,797 | **126** | **−99.91%** |
| 数据库 QPS | 2333.5 | **2.1** | **−99.91%** |
| 错误数 | 0 | 0 | — |

### 6.3 结论

1. **吞吐提升约 10 倍、平均延迟降到 1/10**：同一批接口在 20 并发下 QPS 从 656 提升到 6518，
   平均延迟从 30.75 ms 降到 3.07 ms；
2. **数据库压力下降 99.9%**：同样时间内数据库语句数从 13.98 万降到 126 条
   （DB QPS 2333 → 2.1），说明读流量几乎全部被缓存承接 —— 这是缓存最核心的价值，
   也是系统从"单机小流量"走向"可支撑更多用户"的关键；
3. **推荐接口提升最明显（11.2×）**：因为它本来最"贵"（三路打分 + 聚合查询），
   缓存收益与计算成本成正比；
4. **P95/P99 明显收敛**：缓存关闭时 P99 达 44~50 ms（受 MySQL 连接池与锁竞争影响），
   开启后稳定在 6 ms 左右，尾部延迟改善明显。

> 测量说明（论文中应如实标注）：本实验为**单机环境**、演示数据集（14 件商品 / 4 个用户），
> 应用、Redis、MySQL 同机部署，绝对 QPS 数值高于真实多机部署场景；
> 这里关注的是**同一环境下开关缓存的相对提升**与**数据库减压比例**，该结论不受机器规格影响。

### 6.4 复现方式

```bash
# 1) 缓存开启（默认配置）
cd backend && mvnw.cmd spring-boot:run
python tools/load-test.py --label cache-on --duration 15 --concurrency 20

# 2) 缓存关闭（同一份代码，仅改开关）
mvnw.cmd spring-boot:run -Dspring-boot.run.arguments=--campus.cache.enabled=false
python tools/load-test.py --label cache-off --duration 15 --concurrency 20
```
结果保存在 `tools/load-test-<label>.json`（含逐场景明细与生成时间）。

## 七、可优化方向（论文"展望"可用）

1. **热点 Key 本地缓存**：在应用内加 Caffeine 一级缓存，减少 Redis 网络往返（多级缓存）；
2. **缓存预热**：定时任务在秒杀/开学季前把热门商品刷入缓存，避免冷启动抖动；
3. **滑动窗口 / 令牌桶限流**：当前为固定窗口，临界点可能出现 2 倍突发流量，可升级为滑动窗口；
4. **Redis 集群与持久化**：生产环境采用主从 + 哨兵，缓存数据可接受丢失（RDB 关闭），
   但热门榜等有状态数据可开启 AOF；
5. **缓存命中率监控**：接入 Spring Boot Actuator + Micrometer，暴露命中率、Key 数量等指标，
   配合 Grafana 做可视化；
6. **读写分离**：进一步用 MySQL 主从把读流量分担出去，与缓存形成两级防护。
