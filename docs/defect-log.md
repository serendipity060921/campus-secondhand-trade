## 四、v0.16 阶段缺陷（本表详列）

### BUG-16-01【高 · 逻辑缺陷】分类索引解析错误，33 个分类编号全部错乱

| 项 | 内容 |
| --- | --- |
| 发现方式 | 补充"扁平结构"形态的单元测试时暴露 |
| 现象 | 首页分类色带渲染出 33 段（预期 8 段）；所有商品的分类编号全部落到兜底值 `ZZ`，与分类完全对不上 |
| 复现步骤 | 1) 打开首页 → 观察色带段数；2) 查看任意目录卡的分类编号；3) 用分类接口返回值做单测即可稳定复现 |
| 根因 | 前端分类索引函数只兼容"带 `children` 的树形结构"，而分类接口实际返回**扁平列表 + `parentId`**（一级分类 `parentId=0`）。于是 33 个节点全部被当成一级分类，子分类无法继承父级分类号 |
| 影响 | 全部商品的分类号与色带错误，属于界面信息正确性问题（不影响交易数据） |
| 修复 | 索引函数同时兼容树形与扁平两种形态：`parentId` 为 `0` / `null` / 缺省均视为一级分类，并按 `sortOrder` 排序 |
| 验证 | 新增 8 条"扁平结构"断言（单元测试 20 → 31 条）；页面恢复 8 段色带，子分类编号正确继承（如专业课教材 → G4） |
| 预防 | 接口返回结构的两种形态均纳入单元测试；后续接口结构调整需同步补测 |
| 状态 | ✅ 已修复并验证 |

### BUG-16-02【中 · 功能缺失】聊天页已读回执从未渲染

| 项 | 内容 |
| --- | --- |
| 发现方式 | 功能走查 + 评审意见核实 |
| 现象 | 自己发出的消息看不到"已读/未读"状态，用户无法判断对方是否看过 |
| 复现步骤 | A 给 B 发消息 → B 打开会话（后端已标记已读）→ A 侧消息仍无任何已读标识 |
| 根因 | 数据与链路完全正常：消息表有 `is_read` 字段、后端有标记已读接口、前端也订阅了已读回执 —— **但模板中从未渲染这块状态**，链路齐全却不出结果 |
| 影响 | 功能等于不存在；用户对"对方是否看到"无反馈 |
| 修复 | 在我发出的最后一条消息下渲染"已读/未读"，并补充无障碍标签 |
| 验证 | 浏览器实测消息列表读出已读状态为「已读」；按同一商品连发多条消息时，商品引用条由 3 条去重为 1 条（顺带修复的重复展示问题） |
| 预防 | 此类"链路齐全但缺一环"的缺陷靠读代码或看接口返回都发现不了，必须走真实界面；已纳入功能走查清单 |
| 状态 | ✅ 已修复并验证 |

### BUG-16-03【高 · 逻辑缺陷】站内跳转后整页空白

| 项 | 内容 |
| --- | --- |
| 发现方式 | 端到端回归（31 条中失败 4 条） |
| 现象 | 站内点击商品卡片跳转详情页后，页面完全不渲染：浏览器地址已变化，内容空白；手动刷新后又正常 |
| 复现步骤 | 首页 → 点击任意商品卡片 → 页面空白 |
| 定位过程 | 回归失败集中在"站内跳转"用例；用版本 A/B 对照（暂存本轮改动后复跑）确认是本轮引入，而非既有问题；再逐层排除数据加载（接口返回 200）后定位到渲染层 |
| 根因 | 路由过渡动画要求每个页面组件**只有一个根节点**，而错误态被写成了与内容并列的根级兄弟节点，导致组件变成多根 —— 过渡动画无法接管，页面停在"未渲染"状态 |
| 影响 | 站内所有跳转均不可用（高危，用户无法进入详情页） |
| 修复 | 错误态与内容改为互斥分支（同一根节点下 `if / else`），恢复单根结构 |
| 验证 | 端到端恢复 31/31 全部通过 |
| 预防 | 把"路由组件必须单根"写入项目设计规范（`DESIGN.md` 的 Single Root Rule），避免同类问题再次引入 |
| 状态 | ✅ 已修复并验证 |

### BUG-16-04【中 · 界面与可访问性】正文小字误用装饰性色值，对比度回归

| 项 | 内容 |
| --- | --- |
| 发现方式 | 自动化可访问性审计 |
| 现象 | 正文对比度不达标项由 3 处升至 15 处；目录卡的分类小字实测对比度仅 3.31:1（AA 要求 4.5:1） |
| 根因 | 重构中使用了两级灰色令牌，其中 `--ct-text-faint` 按设计规范**仅用于装饰性文字、不得用于正文**，却被用于 11px 的正文小字 |
| 影响 | 低视力用户难以辨识该文字；同时违反项目自身的设计规范 |
| 修复 | 改用 `--ct-text-muted`（实测 5.85:1），并保留原令牌的适用范围说明 |
| 验证 | 对比度不达标项回到 3 处（均为装饰性文字），不达标率 0% |
| 预防 | 令牌的适用范围写入 `DESIGN.md`；可访问性审计纳入 CI |
| 状态 | ✅ 已修复并验证 |

### BUG-16-05【低 · 构建与工程】非法模板组合与失效事件绑定

| 项 | 内容 |
| --- | --- |
| 发现方式 | 静态检查 + 构建报错 |
| 现象 | 同一元素上同时使用互斥指令；事件绑定指向已不存在的函数（点击无反应） |
| 根因 | 批量重构脚本改动后未逐一复核，遗留了互斥指令组合与失效绑定 |
| 影响 | 局部交互失效；构建阶段即报错，不会进入生产 |
| 修复 | 移除互斥指令组合，事件绑定改为指向实际存在的处理函数 |
| 验证 | 构建通过、静态检查 0 错误、相关交互实测正常 |
| 预防 | 禁止脚本化批量改写后不复核；改动后必须构建 + 静态检查 + 实测三步走 |
| 状态 | ✅ 已修复并验证 |

### BUG-16-06【中 · 构建与工程】CI 流水线失败

| 项 | 内容 |
| --- | --- |
| 发现方式 | 推送后在 GitHub 仓库页观察到 CI 失败状态 |
| 现象 | 三个作业中前端作业失败，仓库页显示红色叉号；而本地逐条复现全部通过 |
| 根因 | ① **Node 20 与 pnpm 11 不兼容**（pnpm 11 要求 Node ≥ 22），而工作流写的是 `node-version: 20`；② `pnpm/action-setup` 排在 `setup-node` 之前，会在 runner 默认的旧 Node 上安装 pnpm 并自检失败；③ `backend/mvnw` 在 git 中权限位为 `100644`（不可执行），改用 `./mvnw` 后会 `Permission denied` |
| 影响 | 流水线不可用，质量门禁形同虚设；对外呈现为"CI 失败的项目" |
| 修复 | ① Node 版本对齐到本地验证过的 24；② 调整步骤顺序为"先 setup-node、再 action-setup"（放弃 pnpm 缓存以换取正确顺序）；③ `mvnw` 权限位改为 `100755`，后端作业改用仓库自带的 Maven Wrapper |
| 验证 | 修复后三个作业全部通过；另用全新克隆复核 `pnpm install --frozen-lockfile` 与后端打包均成功 |
| 预防 | "本地全过、CI 全挂"应优先怀疑版本与权限假设；工作流改动后在全新克隆中复现一遍 |
| 状态 | ✅ 已修复并验证 |

## 五、根因分析与预防措施

| 根因类型 | 涉及缺陷 | 已落地的预防措施 |
| --- | --- | --- |
| 只覆盖单一输入形态 | BUG-16-01 | 接口返回结构的多种形态（树形/扁平/缺省）均纳入单元测试 |
| "链路齐全但缺一环" | BUG-16-02 | 功能走查清单化：数据层、接口层、渲染层逐层确认 |
| 框架隐性约束未文档化 | BUG-16-03 | 写入设计规范（Single Root Rule）；端到端回归作为兜底 |
| 规范知晓但执行走样 | BUG-16-04 | 令牌适用范围写进设计文档；可访问性审计进 CI |
| 批量改写后未复核 | BUG-16-05 | 改动后强制"构建 + 静态检查 + 实测"三步 |
| 环境与权限假设 | BUG-16-06 | 工作流改动后在全新克隆复现；CI 阈值只许下降（棘轮机制） |

**整体趋势**：缺陷从"功能与安全类"（v0.05 ~ v0.10）转向"界面质量与工程效率类"（v0.16），
说明功能正确性已稳定，问题集中在质量工程与协作流程上 —— 这也是本项目把质量门禁接入 CI 的直接动因。
