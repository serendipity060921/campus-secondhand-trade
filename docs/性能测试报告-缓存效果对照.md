# 性能测试报告 · 缓存效果对照实验

> 校园二手交易平台 · 对象：`tools/load-test.py`（开缓存 / 关缓存对照）
> 测试时间：2026-10-09 · 单机部署形态（Nginx 8081 → 后端 jar 8080 → MySQL 8.4 + Redis）

## 一、测试目的

论证本平台引入 Redis 缓存的**实际收益**，并回答两个具体问题：

1. 缓存开启后，接口吞吐与延迟改善多少？
2. 缓存对**数据库压力**的削减有多大？（这是缓存最重要的价值，但最容易被忽略）

## 二、测试方法

| 项 | 设置 |
| --- | --- |
| 工具 | `tools/load-test.py`（自研，基于 `http.client` 长连接多线程压测） |
| 场景 | 首页商品列表 / 商品详情 / 猜你喜欢（推荐）/ 分类列表 —— 均为只读高频接口 |
| 压力 | 每场景 **15 秒 × 20 并发线程**，线程内复用 HTTP 长连接（排除建连开销） |
| 指标 | QPS、平均延迟、P50 / P95 / P99 / 最大延迟、错误数 |
| 数据库压力 | 通过 MySQL `SHOW GLOBAL STATUS LIKE 'Questions'` 前后差值计算**数据库 QPS** |
| 对照变量 | 仅切换 `campus.cache.enabled`（`CACHE_ENABLED` 环境变量），**业务代码零改动** |

复现命令：

```bash
# ① 开缓存（默认）
python tools/load-test.py --label cache-on  --host 127.0.0.1 --port 8080 --duration 15 --concurrency 20

# ② 关缓存：以 CACHE_ENABLED=false 重启后端后
python tools/load-test.py --label cache-off --host 127.0.0.1 --port 8080 --duration 15 --concurrency 20
```

原始数据：`tools/load-test-cache-on.json`、`tools/load-test-cache-off.json`

## 三、测试结果

| 场景 | 开缓存 QPS | 关缓存 QPS | 吞吐提升 | P95（开） | P95（关） | 数据库 QPS（开） | 数据库 QPS（关） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 首页商品列表 | 3184.9 | 1285.1 | **2.48×** | 10.04 ms | 33.24 ms | 8.7 | 5146.3 |
| 商品详情 | 4492.6 | 503.4 | **8.92×** | 7.98 ms | 51.44 ms | 0.6 | 3020.5 |
| 猜你喜欢（推荐） | 4087.9 | 3103.8 | 1.32× | 8.24 ms | 12.05 ms | 5.6 | 9312.3 |
| 分类列表 | 4407.0 | 3517.2 | 1.25× | 8.19 ms | 10.81 ms | 5.4 | 10551.8 |
| **合计** | **4043.4** | **2101.8** | **1.92×** | — | — | **5.1** | **7006.2** |

补充：全程 **错误数 0**；平均延迟由 **16.84 ms 降至 5.04 ms**（下降约 70%）；
总请求数 125,643 → 241,757（同时间内完成量提升近一倍）。

## 四、结论与分析

### 1. 缓存的核心价值是「保护数据库」，而不只是「变快」

关缓存时数据库 QPS 高达 **7006**，开缓存后仅 **5.1** —— **数据库压力下降 99.93%**。
这说明缓存把绝大多数重复读请求挡在了数据库之前。对真实校园场景（下课、毕业季的访问尖峰）而言，
这意味着**数据库不会成为第一批被打垮的组件**。

### 2. 对「单次查询最重」的接口收益最大

商品详情是**单条商品 + 分类 + 卖家 + 图片**的关联查询，开缓存后 QPS 提升 **8.92×**、P95 从 51 ms 降到 8 ms。
而推荐与分类列表的 SQL 相对简单（命中索引即可），因此吞吐提升有限（1.25–1.32×），
但它们的**数据库压力同样被削减了三个数量级**（9312→5.6、10552→5.4）。

### 3. 延迟分布更稳定

P99 由最高 86 ms 收敛到 16 ms 以内，说明缓存不仅提高均值，也**消除了长尾**（数据库抖动不再直接传导到用户）。

### 4. 可复现性与可验证性

对照实验只改一个环境变量（`CACHE_ENABLED`），**业务代码零改动** —— 这本身也是本平台"配置化开关"设计的验证。

## 五、局限性（如实说明）

| 局限 | 说明 |
| --- | --- |
| 单机、本机回环 | 未包含真实网络延迟；生产环境下绝对数值会下降，但**相对结论不变** |
| 只测只读接口 | 写接口（发布/下单）未纳入，缓存对写路径的影响未评估 |
| 短时压测 | 每场景 15 秒，未评估缓存**过期瞬间的击穿**与长时间稳定性 |
| 单机数据库 | MySQL 与压测程序同机，数据库 QPS 的绝对值受 CPU 竞争影响 |
