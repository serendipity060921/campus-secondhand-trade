# 数据库性能与索引审查

> 校园二手交易平台 · v0.18 / 第1批-④
> 复跑：`python tools/index-review.py`（自动建库灌数 + 逐条 EXPLAIN，不触碰生产库）
> 迁移：`db/schema/05-index-tuning.sql`　原始数据：`docs/数据库性能与索引审查-数据.json`

## 一、为什么要"另建一个库"来审查索引

如果直接对演示库跑 `EXPLAIN`，会得到**假阳性**：所有表只有 3~33 行，
优化器在这个量级下**必然选择全表扫描**（走索引反而更慢），
于是每条查询都显示 `type=ALL`，看着像"到处缺索引"，其实什么也说明不了。

因此本次审查：

1. 新建独立库 `campus_trade_perf`，用 `CREATE TABLE ... LIKE` **克隆** 11 张表
   （结构与生产库完全一致，**含全部现有索引**）；
2. 灌入接近真实的量级（用递归 CTE 批量生成，约 1 分钟）：

| 表 | 行数 | 表 | 行数 |
| --- | ---: | --- | ---: |
| product | 50,000 | message | 50,000 |
| user_behavior | 200,000 | favorite | 30,000 |
| product_image | 100,000 | orders | 20,000 |
| moderation_log | 30,000 | user | 5,000 |
| admin_log | 2,000 | report | 500 |

3. 对项目**真实使用的 21 种查询形态**逐条 `EXPLAIN`，再用 `EXPLAIN ANALYZE` 看**实际耗时**。

> 生产库全程未被改动，数据不变量复核通过（4/17/4/4/9）。

## 三、★ 逐条追查：6 条"关注"里只有 1 条是真问题

这一节是本文档最有价值的部分 —— **看着像问题的，多数经实测后并不值得改**。

### 3.1 ✅ 采纳：商品按价格排序（唯一真正值得加的索引）

```
优化前：type=ref  key=idx_status        rows=24876  Extra=Using filesort
优化后：type=ref  key=idx_status_price  rows=24876  Extra=Using where
EXPLAIN ANALYZE（加索引后）：
  -> Limit: 12 row(s) (actual time=2.95..2.96 rows=12 loops=1)
      -> Index lookup on product using idx_status_price (status=1) (actual time=2.95..2.95 rows=12)
```

**实际只读取 12 行、耗时 2.96 ms**；优化前需要把 24,876 行取出后排序。
已通过迁移 `05-index-tuning.sql` 加到生产库。

### 3.2 ✗ 拒绝：商品列表(分类) —— 加索引反而更慢

本来打算把 `idx_status_category(status, category_id)` 扩展成
`(status, category_id, create_time)` 以消除 filesort。加完再测：

```
加索引后：type=ref key=idx_status_category_time rows=1440
不加索引：type=index key=idx_create_time        rows=414
EXPLAIN ANALYZE（不加索引，走 idx_create_time 倒序 + LIMIT 12）：
  -> Limit: 12 row(s) (actual time=0.0642..1.16 rows=12 loops=1)
      -> Index scan on product using idx_create_time (reverse) (actual time=0.0612..1.14 rows=398)
```

**1.16 ms，而且只扫 398 行**。原因：有 `LIMIT 12` 时，倒序索引扫描找到 12 条匹配即可终止；
换成 `(status, category_id, create_time)` 反而要扫 1440 行。**结论：不加。**

> ★ **方法论教训**：`Using filesort` **不等于**性能问题。小 `LIMIT` 下 MySQL 用优先队列排序，
> 代价极低。判断必须看 `EXPLAIN ANALYZE` 的**实际耗时与实际读取行数**，
> 而不是看 `Extra` 里有没有 `filesort`。这一条推翻了我最初的判断。

### 3.3 ✗ 拒绝：买家/卖家订单列表 —— 改动之后优化器根本不用

把 `(buyer_id, status)` / `(seller_id, status)` 换成带 `create_time` 的版本后重测：

```
卖家订单(按状态)：type=ref key=idx_seller_status rows=4 Extra=Using filesort
```

优化器**仍然选择原索引**并做 filesort（只有 4 行需要排序）。也就是说换了索引也改变不了执行计划，
**改动无收益 → 已撤回**，订单表索引保持原样。

### 3.4 ✗ 拒绝：收藏夹列表 / 我的商品 —— 排序的行数本来就只有几行

- 收藏夹：`uk_user_product(user_id, product_id)` 已能按 `user_id` 定位，实测命中 **6 行**，
  单个用户的收藏量天然有限，排序代价可忽略；
- 我的商品：实测命中 **10 行**，同理。

> 原本想用"给某个卖家造 5000 件商品"的偏斜场景来证明加索引的收益，
> 但造数脚本没成功。**没有证据就不加索引** —— 索引不是免费的，
> 每个索引都要付出写入与维护成本。（这一取舍已写进迁移文件的"拒绝清单"。）

### 3.5 ✗ 拒绝：会话列表的 OR 条件 —— 属该查询形态的固有代价

`WHERE from_user_id=? OR to_user_id=?` 无法用单个索引消除排序，
优化器已选择 `index_merge + sort_union`（实测 20 行），这是合理方案。
若将来会话量级剧增，可考虑改写成两条查询 `UNION ALL` 再排序，但不属于索引层面能解决的事。

### 3.6 ✗ 不在范围内：关键词模糊查询

`LIKE '%教材%'` 前置通配符无法走索引 —— 这是设计取舍（校园场景关键词量小，
且已有分类与排序兜底）。若确实需要，应引入 MySQL 全文索引或 Elasticsearch，
不属于本次索引调整范围。

## 四、最终结论

| 项 | 结果 |
| --- | --- |
| 审查查询形态 | **21 种** |
| 初始"需关注" | 6 条 |
| **采纳索引** | **1 个**：`product.idx_status_price (status, price)` |
| 拒绝（附实测理由） | 5 条 |
| 生产库改动 | 仅新增 1 个索引，**未删除任何既有索引**，数据未变（不变量复核 ✓） |
| 迁移脚本 | `db/schema/05-index-tuning.sql`（含拒绝清单与回滚脚本） |
| 基础 schema | `db/schema/01-schema.sql` 已同步，全新部署即含该索引 |

## 五、局限（如实说明）

1. **数据是合成的**：行数按真实量级生成，但分布（如商品与卖家的关系）是构造的，
   与真实校园场景的偏斜程度不同；
2. **单机单连接**：`EXPLAIN ANALYZE` 反映的是无并发下的执行代价，
   不包含锁竞争与并发下的表现（并发能力另见 `docs/性能测试报告-缓存效果对照.md`）；
3. **未覆盖全部查询**：21 条覆盖了主要读写路径，但管理端统计类查询只取了机审统计一条；
4. 结论仅适用于当前 MySQL 8.4 的优化器行为，升级大版本后应复跑本审查。
