# 前端组件级测试（v0.18 / 第6批-㉒）

> 一句话结论：引入 **Vitest + @vue/test-utils + jsdom**，为双向评价的两个组件写了 **15 条组件测试**，
> 覆盖率 **98.15%**（行/语句），并接入 CI；这是本项目第一次让"UI 行为"进入自动化验证。

- 位置：`frontend/tests/component/`（**放在 frontend 内**，理由见 §2）
- 配置：`frontend/vitest.config.js`
- 运行：`pnpm test:component` / `pnpm test:component:coverage`
- CI：`ci.yml` 的 frontend job 增加「组件级测试（Vitest）」步骤

---

## 一、为什么现在才做，以及为什么必须做

在此之前的自动化版图里，"前端"只有**纯函数**测试（`tests/unit/*.mjs`，76 条）：
索书号规则、发布校验规则这类可以直接 `node` 跑的纯逻辑。

但双向评价这次新增的两块 UI —— 商品评价区、评价弹窗 —— **没有一行被自动验证过**：

| 风险 | 纯函数测试能否发现 |
| --- | --- |
| 评价区把平均分算错、好评率口径错 | ❌ |
| 无数据时一片空白（而不是"还没有评价"） | ❌ |
| 加载失败没有重试入口 | ❌ |
| 星级分布条全贴地（看不出差异） | ❌ |
| 弹窗把"已评价过"当成红色报错 | ❌ |
| **前端偷偷传了 `toUserId`（越权评价）** | ❌ ← 这是最要紧的一条 |

最后一条是安全边界：后端只接受 `orderId`、被评价人由订单推导。
但"前端有没有多传字段"这件事，只有组件测试能在**提交载荷**层面断言。

## 二、为什么测试放在 `frontend/tests/` 而不是仓库根的 `tests/`

第一版我把测试放在仓库根的 `tests/component/`（与 `tests/unit` 一致），结果启动就失败：

```
Error: Failed to resolve import "@vue/test-utils" from "../tests/component/setup.js"
```

原因：**裸模块解析从文件所在目录开始**。仓库根的 `tests/` 下没有 `node_modules`，
`@vue/test-utils` 解析不到。放开 Vite 的 `server.fs.allow: ['..']` 只解决了"能不能读文件"，
不解决"模块能不能解析"。

结论：组件测试放在 `frontend/tests/component/`（这也是 Vitest 项目的惯例位置）。
纯函数测试仍留在仓库根 `tests/unit/`，它们不 import 任何裸模块，用 `node` 直接跑。

## 三、口径与门槛（据实测设定，不拍脑袋）

```js
coverage: {
  provider: 'v8',
  include: ['src/components/evaluation/**'],
  thresholds: { lines: 95, statements: 95, branches: 75, functions: 45 }
}
```

| 决定 | 理由 |
| --- | --- |
| **只统计 `components/evaluation`** | 其余组件暂无组件级测试，算进来会得到一个「很低但无从下手」的整体数（实测 24.49%）。这与后端"排除 Lombok 生成代码"同理：**改变口径必须写明理由**，然后按口径设棘轮 |
| **不含 `src/api/*.js`** | 那些是薄封装（一行一个 axios 调用），组件测试里必然被 `mock`，计入后恒为 0%；其正确性由后端接口的端到端实测负责 |
| 门槛 = 实测向下取整 | 实测 98.15 / 98.15 / 80.70 / 50 → 门槛 95 / 95 / 75 / 45，**只许上升** |
| `functions` 门槛只有 45 | Vue SFC 模板里的内联箭头函数也被 v8 计入，函数覆盖率天生偏低 |

## 四、15 条测试分别守什么

### 4.1 `EvaluationSection.spec.js`（6 条）

| # | 断言 |
| --- | --- |
| 1 | 有数据时渲染平均分 `4.7`、好评率 `66.7%`、条数 `3 条` |
| 2 | 评价内容与标签正确渲染（标签用 ` · ` 连接） |
| 3 | **无头像时用昵称首字兜底**，不裂图（`.avatar-fallback` 恰好 1 个） |
| 4 | 无评价时显示空态，且**不渲染列表** |
| 5 | 加载失败显示错误态；调用 `reload()` 后能恢复（三态可收敛） |
| 6 | ★ **星级分布条按最高档归一化**：5 星最多 → 100%，1 星 1 条 → 50% |

### 4.2 `EvaluationDialog.spec.js`（9 条）

| # | 断言 |
| --- | --- |
| 1 | ★ 已评过（`mine=true`）→ `checkBeforeOpen()` 返回 `false` 并给出提示 |
| 2 | 没评过 → 返回 `true` |
| 3 | 预检查询失败**不阻塞**提交（后端仍做最终校验） |
| 4 | ★ 提交载荷只含 `orderId`，且 **`toUserId` 必须为 undefined**；内容去空格、标签用逗号连接、匿名转 1 |
| 5 | 内容/标签留空时提交 `undefined`，而不是空串 |
| 6 | ★ 后端 `9004`（已评价过）→ 走**友好提示**而非红色报错，且不触发 `submitted` |
| 7 | `9003`（订单未完成）/ `9002`（非买卖双方）各有对应话术 |
| 8 | 未知错误 → 走通用错误提示 |
| 9 | 标签候选来自 `api/evaluation.js`，前后端不各写一份 |

## 五、Element Plus 怎么处理

不真实渲染整套 UI，而是用**轻量 stub**（`frontend/tests/component/setup.js`）：

- `el-dialog` 的 stub **必须渲染 default 与 footer 两个插槽**，否则弹窗里的按钮不在 DOM 里，点不到；
- `el-form / el-form-item / el-checkbox-group` 用渲染默认插槽的通用 stub；
- `el-rate / el-tag / el-switch / el-input` 用占位 stub（断言的是"传了什么/渲染了什么"，不是组件库内部实现）。

这样测试快（15 条 4.7 秒）且稳定，也不会因为 Element Plus 升级而误红。

## 七、局限（如实说明）

| 项 | 状态 |
| --- | --- |
| 只有评价相关 2 个组件有测试 | 其余组件（商品列表/详情/订单/聊天/管理后台）仍无组件级测试 |
| 未覆盖真实网络与路由 | API 全部 mock；路由跳转未测（属端到端范畴） |
| 未跑浏览器端到端 | 本轮仍没跑 E2E（套件打 Nginx 8081，本地未启动） |
| 视觉回归 | 无（不做像素对比） |
| `functions` 覆盖率仅 50% | 模板内联函数被 v8 计入，属口径特性，已在门槛说明中标注 |

**结论**：这一步把"新写的 UI 完全没有自动验证"补成了"两个新组件 98% 行覆盖 + 关键安全断言"，
但**不等于前端整体被测**。真要全面覆盖，需要按同一模式逐个组件补，并补上 E2E。
