# 缓存命中率监控与实测（v0.18 / 第4批-⑯）

> 一句话结论：给 `CacheService` 加了**命中/未命中/异常**三个进程内计数与 `stats()`，
> 并在真实部署上实测到 **热路径命中率 100%（1500 命中 / 0 未命中 / 0 错误）**；
> 同时发现一个**好性质**：不存在的商品在进入缓存之前就被拒绝，因此不会污染缓存。

- 实测时间：2026-10-16
- 实测环境：prod profile，`http://127.0.0.1:8080`，MySQL 8.4 + Redis
- 工具：`tools/cache-hit-rate.py`（零第三方依赖）
- 原始数据：`docs/test-evidence/缓存命中率-数据.json`

---

## 一、为什么要做这件事

之前的性能结论是"开了缓存后吞吐提升 N 倍"（见 [`性能测试报告-缓存效果对照.md`](性能测试报告-缓存效果对照.md)）。
但**吞吐提升**只能说明"缓存起作用了"，说不出**在多大比例上起作用**。
一旦命中率从 99% 掉到 60%，数据库压力会成倍上涨，而吞吐曲线在低负载下**看不出来**。

所以要有一个**能持续观察的指标**：命中率。

## 二、实现（不引入任何新依赖）

改动只有两处：

| 文件 | 改动 |
| --- | --- |
| `service/CacheService.java` | 新增 `Map<String,Object> stats()` 与 `void resetStats()` |
| `service/impl/CacheServiceImpl.java` | 三个 `AtomicLong` 计数 + 在 `get()` 里判定 + 每 500 次读打一行 INFO 日志 |

计数口径（**这三点是监控能不能用的关键**）：

1. **命中** = Redis 里有值且反序列化成功；
2. **未命中** = key 不存在，**或命中了"空值缓存"**（防穿透写入的 NULL 标记）——
   后者虽然是"缓存命中"，但**没有业务数据**，记成命中会让指标虚高；
3. **异常单独计 `error`，不进命中率分母** —— Redis 挂掉时若把异常算成未命中，
   命中率会跳水，人会以为"缓存配错了"，实际是服务故障。两类问题必须分开看。

另外：**关闭缓存时完全不计数**，否则做"开/关缓存对照实验"时，关闭组的计数会混进开启组。

日志形态（每 500 次读一行，不刷屏）：

```
[缓存统计] 累计读=1500 命中=1500 未命中=0 错误=0 命中率=100.0%
```

## 三、实测

### 3.1 热路径（预热 4 个热点商品，1500 次请求）

```bash
python tools/cache-hit-rate.py --requests 1500 --hot 4
```

| 指标 | 数值 |
| --- | ---: |
| 请求数 | 1500 |
| 耗时 | 16.21 s |
| 吞吐 | 约 93 qps（单线程顺序请求，非并发压测） |
| HTTP 5xx / 网络错误 | 0 |
| **命中** | **1500** |
| **未命中** | **0** |
| **错误** | **0** |
| **★ 命中率** | **100.0%** |

说明：这是"**缓存已预热 + 反复访问同一批热点商品**"的场景，对应真实使用中
"首页/详情页被反复打开"的情形，因此 100% 是合理的，不代表全站平均。

### 3.2 未命中方向的验证（由单测覆盖，而不是硬造数据）

原本想用"随机访问不存在的商品"把命中率压下来做对照，实测**没有效果**：
600 次 `GET /api/product/9xxxxx` 之后，计数**完全没有变化**。

反查原因：不存在的商品在**进入缓存逻辑之前**就被业务判为 3001 拒绝，
根本没有发生缓存读。这其实是一个**好性质**：

> 不存在的 ID 不会把 `NULL` 标记写进缓存，也不会产生无意义的缓存读 ——
> 既避免了缓存被随机扫描污染，也让命中率指标不被垃圾流量稀释。

未命中的三个口径（key 不存在 / 空值缓存 / Redis 异常）由
`CacheStatsTest` 的 8 条用例固定，包括"3 命中 1 未命中 = 75%"的比率计算。

## 四、指标怎么用

| 场景 | 观察点 | 处置建议 |
| --- | --- | --- |
| 命中率突然下降 | 是否有人把 TTL 调短、或新增了"读多写少但键名带参数"的接口 | 先看 `error` 是否上升，再看 key 设计 |
| `error` 上升 | Redis 连接/超时 | 这是故障而不是缓存失效；业务已自动降级为查库 |
| 命中率长期 < 80% | 缓存预热不足，或热点分散 | 考虑提高 TTL、或在发布后预热热门商品 |

## 五、局限（如实说明）

1. **单实例、进程内**计数，重启清零；多实例部署时需按实例看，或后续接入 Micrometer 汇总。
   —— 这一点直接写在 `CacheService.stats()` 的 Javadoc 里，避免数字被误读。
2. 只统计 `get()`（含 `getList` 委托），**不包含** `exists()`；
   `exists` 是"先探测再取值"的两段式用法，若也计入会产生"一次业务读算两次"的重复计数。
3. 本次实测是**单线程顺序请求**，93 qps 反映的是本机 HTTP 开销，不是系统容量上限；
   容量与并发结论见 [`性能测试报告-缓存击穿与写路径.md`](性能测试报告-缓存击穿与写路径.md)。
