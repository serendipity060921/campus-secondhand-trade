# 内容治理说明（两层：自动审核 + 人工复核）

> 校园二手交易平台 · 黎钟 · 2027 届软件工程
> 本文说明 v0.17 引入的**内容机审**（内容治理第一层）如何与既有的**管理后台人工审核**（第二层）配合，
> 以及它的规则、验证方式与已知局限。

## 一、为什么需要这一层

原实现只有一个**全局开关** `campus.audit.enabled`：

```java
// v0.13 原实现（ProductModuleServiceImpl）
boolean auditRequired = auditProperties.isEnabled();   // 开 = 所有商品都进「待审核」
```

问题很清楚：**要么全部人工审核（慢，且校园场景下二手教材等商品会错过交易时机），
要么完全不审核（违规内容直接上架）**。而管理后台的「商品审核（通过 / 驳回）」页面
也因此缺少真实的商品来源 —— 没有任何商品会进入「待审核」。

参照主流平台（机审先行 + 人审复核）的做法，本项目把开关改为**按商品风险判定**：

```
发布 → 【第一层 机审】规则判定
         ├─ 未命中      → 直接上架（status = 1 在售）
         ├─ 命中可疑    → 转「待审核」（status = 0）→ 【第二层 人工复核】通过 / 驳回
         └─ 命中违禁    → 直接拒绝发布，返回具体原因
```

## 二、规则表（`ContentModerator`）

| 规则 | 判定依据 | 动作 |
| --- | --- | --- |
| **R1 违禁词** | 学术作弊（代写/代考/替考/包过）、证件票据（代办/办证/假证/发票）、危险物品（管制刀具/气枪/枪支/弹药）、违禁品（毒品/野味）、赌博色情 | **拒绝** |
| **R2 联系方式引流** | 手机号（`1[3-9]\d{9}`）、QQ 号（`qq` + 5 位以上数字）、微信号（微信/vx/v信）、外链（http、www.）、二维码/扫码 | **转人工复核** |
| **R3 价格异常** | 非正数 → 拒绝；超过 10 万元 → 转人工复核 | 拒绝 / 转审 |

**词表策略**：刻意取得**具体**（用「管制刀具」而不是「刀具」，避免误伤菜刀等正常商品），
以控制误报；放行类商品的行为与改动前完全一致。

**归一化**：匹配前统一做「全角转半角 → 去掉所有非字母数字汉字（空格、`*`、`.` 等）→ 转小写」，
因此 `代 写`、`代*写`、全角字符这类规避写法仍能被命中（见测试用例）。

**命中留痕**：每次判定都返回命中明细（规则号、字段、命中词），既用于向用户解释，
也用于统计**漏报与误报**（日志关键字：`[商品发布-机审拒绝]` / `[商品发布-转人工复核]`）。

## 三、与既有代码的衔接（改动很小）

| 文件 | 改动 |
| --- | --- |
| `common/moderation/ContentModerator.java` | 新增：机审器（纯函数，规则表 + 归一化） |
| `common/moderation/ModerationAction.java` | 新增：PASS / REVIEW / REJECT |
| `common/moderation/ModerationResult.java` | 新增：结果 + 命中明细 + 可展示原因 |
| `common/result/ProductResultCode.java` | 新增错误码 `CONTENT_REJECTED(3010)` |
| `common/exception/ProductException.java` | 新增工厂方法 `contentRejected(detail)` |
| `service/impl/ProductModuleServiceImpl.java` | 发布时先机审：拒绝则抛异常；可疑则复用既有 `auditRequired` 走「待审核」 |
| `views/product/Publish.vue` | 返回 status=0 时提示「已提交，平台审核通过后即可展示」 |

**关键点**：复用了 v0.13 就预留好的 `auditRequired` 分支，因此
**未命中风险的正常商品行为完全不变** —— 这也是既有 31 条端到端测试能全绿的原因。

## 五、答辩演示（2 分钟，可现场操作）

1. 打开发布页，正常填写并发布一件商品 → **直接出现在首页**（说明第一层放行，效率不受影响）。
2. 再发布一件，标题写「专业代写论文包过」→ **发布被拒绝**，提示里明确指出命中了什么。
3. 再发布一件，描述里留一个手机号 → 提示「**已提交，平台审核通过后即可展示**」，
   商品此时为「待审核」；登录 `admin/123456` 进管理后台 → 商品管理 → **审核通过** →
   回到首页，商品出现。

**讲解口径**：机审保证效率（毫秒级、规则可回归），人审兜底复杂判断（可追溯、可驳回）。

## 六、已知局限与后续方向

| 局限 | 说明与后续做法 |
| --- | --- |
| 规则表需人工维护 | 词表集中在 `ContentModerator`，可外置为配置/数据库表以便运营调整 |
| 未做图片内容审核 | 当前只审标题与描述；后续可接入图片识别或哈希黑名单 |
| 类目黑名单未启用 | `moderate(...)` 已保留 `categoryId` 参数，规则表可直接扩展 |
| 漏报/误报未量化 | 命中明细已落日志，后续可统计"转审率、误报率"并据此调词表 |
| 词表可能误伤 | 已按"具体词优先"设计；仍建议对 REJECT 命中保留人工申诉入口 |
