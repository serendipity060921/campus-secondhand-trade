# 校园二手交易平台 · 管理后台设计说明（v0.13）

> 本文是论文"系统实现 / 后台管理模块"章节的素材：说明管理后台的功能划分、权限控制、
> 数据看板指标与聚合方式、商品审核状态机、举报处理流程，以及开发过程中发现的问题与修复。

---

## 一、模块定位

前十二个版本都在做"面向买家/卖家"的前台业务。v0.13 补齐了**平台运营方**这一角色：
没有后台，平台方无法审核违规商品、无法处置举报与恶意用户，也无法掌握整体运营数据。

| 能力 | 说明 | 对应角色 |
| --- | --- | --- |
| 数据看板 | 概览指标、近 7 天趋势、分类/状态分布（ECharts 可视化） | 管理员 |
| 商品管理 | 全状态商品查询、审核（通过/驳回）、强制下架 | 管理员 |
| 用户管理 | 用户查询、启用/禁用、发布与成交统计 | 管理员 |
| 举报处理 | 举报列表、处理/忽略并留痕 | 管理员 |
| 举报提交 | 在商品详情页举报违规商品 | 登录用户 |
| 操作日志 | 记录管理端所有写操作，可追溯 | 管理员 |

## 二、权限控制：前后端双层校验

```
浏览器访问 /admin/**
   │
   ├─ 前端路由守卫（router.beforeEach）
   │     meta.requiresAuth  → 无 Token 跳登录页
   │     meta.requiresAdmin → role !== 1 提示"需要管理员权限"并跳回首页
   │
   └─ 后端 @LoginRequired(admin = true)（AdminController 类级别）
         LoginInterceptor 解析 JWT → UserContext
         未登录 → 401；已登录但 role !== 1 → 403「没有操作权限」
```

**为什么必须双层？** 前端守卫只是用户体验优化，攻击者可以用 curl 直接调用接口；
后端注解才是真正的安全边界。测试用例 A1~A4 正是按此设计验证：
未登录 5 个后台接口全部 401、学生 Token 全部 403、写接口同样 403。

## 三、数据看板

### 3.1 指标体系

| 分组 | 指标 |
| --- | --- |
| 规模 | 用户总数、商品总数、在售商品数、订单总数、已完成订单数、私信总数、收藏总数 |
| 交易 | 累计成交额（仅已完成订单）、近 7 天成交额 |
| 增长 | 今日新增用户、今日新增商品、今日新增订单、近 7 天趋势曲线 |
| 待办 | 待审核商品数、待处理举报数（后台菜单红点 + 看板顶部提醒） |
| 结构 | 商品分类分布（饼图）、订单状态分布、商品状态分布（环形图） |

### 3.2 聚合方式：统计下推到数据库

看板的全部聚合都用 SQL 完成（`AdminStatMapper`），应用层只做"补齐空缺日期"这类轻量加工：

```sql
-- 近 7 天每日订单数与成交额（金额只算已完成订单）
SELECT DATE_FORMAT(create_time,'%Y-%m-%d') AS label, COUNT(*) AS value,
       IFNULL(SUM(CASE WHEN status = 3 THEN amount ELSE 0 END), 0) AS amount
FROM orders WHERE deleted = 0 AND create_time >= #{since}
GROUP BY label ORDER BY label;
```

**为什么不让应用层统计？** 如果把明细数据 `SELECT *` 拉到 Java 里再遍历统计，
数据量增长后内存与网络开销会失控（几万条订单就要全表传输）。
"能在数据库算的不要在应用算"是大屏/报表类需求的通行做法。

**为什么要补齐日期？** SQL 的 `GROUP BY` 只会返回"有数据的日期"，
若某天没有新增用户，折线图会出现断点。因此按最近 7 天生成完整日期骨架、
缺失的日期补 0（`fillMissingDays`）。

### 3.3 前端可视化

- 使用 **ECharts 6**（按需引入 `echarts/core` + LineChart/PieChart/BarChart + 必要组件，避免整包）；
- 图表在数据返回后再初始化（`setTimeout` 等 DOM 渲染完成），组件卸载时 `dispose` 释放实例，
  窗口 `resize` 时统一 `resize()`；
- 趋势图用双 Y 轴：左轴数量（用户/商品/订单），右轴金额（成交额柱状）。

## 四、商品审核

### 4.1 状态机

```
                    ┌─────────────┐
   卖家发布商品 ───→ │ status = 0  │  待审核（前台不可见、详情对非本人 3001）
 （审核开关打开时）   └──────┬──────┘
                            │ 管理员审核
              ┌─────────────┴─────────────┐
         通过 │                            │ 驳回（填写理由）
              ↓                            ↓
      ┌─────────────┐              ┌─────────────┐
      │ status = 1  │ 在售         │ status = 2  │ 审核不通过（audit_remark 说明原因）
      └──────┬──────┘              └─────────────┘
             │ 被下单
             ↓
      ┌─────────────┐   订单完成    ┌─────────────┐
      │ status = 4  │ ───────────→ │ status = 5  │ 已售出
      │   交易中    │              └─────────────┘
      └─────────────┘
             ↑ 取消订单回到 1
      ┌─────────────┐
      │ status = 3  │ 已下架（卖家下架 / 管理员强制下架）
      └─────────────┘
```

### 4.2 实现要点

| 要点 | 做法 |
| --- | --- |
| 复用既有字段 | `auditor_id` / `audit_time` / `audit_remark` / `shelf_time` 在 v0.02 设计数据库时已预留，本版本直接启用，**无需改表** |
| 只允许审核待审核商品 | 非 `status = 0` 返回 8003，避免对已售出商品改状态 |
| 审核留痕 | 每次审核写入 `admin_log`（操作人、商品、结果、意见） |
| 缓存联动 | 审核后调用 `CacheEvictor.productChanged()`，列表/详情/推荐缓存立即失效（v0.12 能力复用） |
| 前台可见性 | 待审核商品不在列表中出现，匿名访问详情返回 3001（v0.10 的 BUG-02 修复已保证） |
| 审核开关 | `campus.audit.enabled`：默认 `false`（发布即上架，兼容既有流程）；设为 `true` 时新发布商品进入待审核 |

> **设计取舍说明（论文可写为"可配置的业务流程"）**：
> 真实校园平台通常要求先审后发。但本项目 v0.05~v0.12 的商品发布流程、自动化用例与前端交互
> 都建立在"发布即可见"之上，直接改成强制审核会破坏前序版本的行为契约。
> 因此把审核做成**开关**：默认保持兼容，答辩演示时打开开关即可展示完整的"发布 → 待审核 → 审核通过 → 上架"闭环，
> 这样既补齐了业务流程，又满足"新版本不破坏既有功能"的工程约束。

## 五、举报处理

| 环节 | 说明 |
| --- | --- |
| 提交 | 用户在商品详情页点「举报商品」，选择原因（虚假信息/违禁物品/辱骂骚扰/其他）+ 补充说明；接口 `POST /api/report/submit`，限流 10 次/10 分钟 |
| 校验 | 对象不存在 → 8007；举报自己的内容 → 8006 |
| 查询 | 用户查自己的举报 `GET /api/report/mine`；管理端按状态筛选 `GET /api/admin/report/list` |
| 处理 | 管理员「处理/忽略」并填写处理结果 → `status = 1/2`，记录处理人与时间 |
| 幂等 | 已处理的举报再次处理 → 8002（避免重复操作覆盖处理结论） |
| 留痕 | 每次处理写入 `admin_log` |

| 功能 | 说明 |
| --- | --- |
| 列表 | 支持用户名/昵称/学号/手机号关键词、角色、状态筛选；每条记录附带**发布商品数、成交订单数、被举报数**（用 3 次 `GROUP BY` 批量统计，避免 N+1） |

## 七、操作日志（审计）

`admin_log` 记录四个关键动作，字段包含操作人、动作、对象类型与 ID、详情、IP、时间：

| action | 触发场景 | 示例详情 |
| --- | --- | --- |
| `AUDIT_PRODUCT` | 商品审核 | 审核通过：《计算机网络（第7版）》教材；意见：资料完整 |
| `OFFLINE_PRODUCT` | 强制下架 | 强制下架：某网课账号；原因：涉嫌违规商品 |
| `DISABLE_USER` / `ENABLE_USER` | 用户启用禁用 | 禁用用户：stu_demo |
| `HANDLE_REPORT` | 处理举报 | 处理举报：举报属实，已下架该商品 |

日志写入采用"业务成功后旁路记录、失败只记 warn"的方式，**不会因为日志表异常导致审核失败**。

## 九、开发中发现并修复的问题

### 问题 1：不可变 Map 遇到 null 查询抛 NPE（提交举报 500）

- **现象**：普通用户提交举报返回 500「服务器内部错误」。
- **定位**：日志 `NullPointerException: Cannot invoke "Object.equals(Object)" because "o" is null`，
  位置在举报 VO 转换：`nameMap.get(report.getHandleAdminId())`。
- **原因**：未处理的举报 `handle_admin_id` 为 `null`（这是正常业务状态），
  而该 Map 是用 `Map.of(k, v)` 创建的**不可变 Map** —— 它对 null 键/值都敏感，
  用 `null` 去 `get()` 会直接抛 NPE，而不是像 `HashMap` 那样返回 `null`。
- **修复**：改用 `HashMap` 构造映射，并在查询前判空。
- **启示**：JDK 9+ 的 `Map.of`/`List.of` 是"空值不友好"的，适合确定无 null 的场景；
  业务数据（数据库字段可空）映射时用 `HashMap` 更安全。

### 问题 2：测试数据清理模式误伤演示账号

- **现象**：v0.13 用例跑完后，演示账号 `admin` 的 1 条收藏、1 条私信、3 条行为记录消失。
- **原因**：清理脚本使用 `username LIKE 'ad%'` 删除测试账号，
  但该模式同时匹配了演示账号 **admin**（`ad` + `%`）；其中删除用户因外键约束回滚失败，
  而删除收藏/私信/行为的语句成功执行，于是"测试数据没清掉、演示数据反被删"。
- **修复**：清理模式改为精确正则 `^ad[0-9a-f]{5}$`（测试账号为 `ad` + 5 位十六进制），
  并重建了被误删的数据（收藏计数已重算校验一致）。
- **启示**：自动化测试的清理语句必须**精确匹配**测试数据特征（前缀+长度/正则），
  绝不能用宽松的 `LIKE 'xx%'`；同时应避免测试账号前缀与业务账号冲突（如 `ad` 与 `admin`）。

## 十一、后续可扩展方向

1. **审核工作流**：支持驳回后卖家编辑重新提交、审核队列分配、超时提醒；
2. **举报与处罚联动**：举报属实可自动扣减信用分、累计 N 次自动下架/封禁；
3. **数据导出**：看板数据导出 Excel、按月生成运营报表；
4. **更细的权限模型**：引入 RBAC（角色-权限-菜单），支持"客服/审核员/超级管理员"多角色；
5. **实时看板**：用 WebSocket/SSE 推送今日实时订单与在线人数（与 v0.14 实时私信共用通道）；
6. **敏感词与图片审核**：发布时自动检测违禁词，接入图片内容识别，减少人工审核量。
