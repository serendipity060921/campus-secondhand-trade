# 校园二手交易平台 · 推荐算法设计与实验（v0.11）

> 本文是论文"个性化推荐模块设计与实现"章节的素材：包含算法选型理由、数据模型、
> 打分公式、参数配置、离线评测协议与实验结论。所有数据均由 `tools/recommend-eval.py` 实测产出。

---

## 一、为什么要在校园二手交易场景做推荐

校园二手交易有三个显著特点，决定了推荐模块的必要性：

1. **商品生命周期短**：一件二手商品通常几天内就成交或被下架，热门排序会让新发布的商品得不到曝光；
2. **用户兴趣高度集中**：学生群体兴趣围绕专业（教材）、宿舍（生活用品）、数码、运动等少数主题，
   兴趣可建模性强，内容召回效果明显；
3. **行为稀疏但意图明确**：用户量小、行为少（很多人只看一两件），因此必须**多路召回**——
   行为足够时靠协同过滤，行为稀疏时靠内容匹配，完全无行为时靠热门度冷启动。

因此本模块采用 **多路召回 + 加权融合排序** 的架构，而不是单一算法。

## 二、数据模型：用户行为表

推荐的数据源是新增的 `user_behavior` 表（8 张表中的第 8 张）：

| 字段 | 说明 |
| --- | --- |
| `user_id` / `product_id` | 行为主体与客体 |
| `behavior_type` | 1 浏览 / 2 收藏 / 3 私信（询价）/ 4 下单 |
| `weight` | 兴趣强度权重，默认 **浏览 1 / 私信 2 / 收藏 3 / 下单 5** |
| `category_id` | 冗余商品分类，便于按分类聚合用户偏好（省一次 JOIN） |
| `behavior_count` | 同类行为累计次数（频次信号） |
| `create_time` / `update_time` | 首次/最近发生时间，用于时间衰减 |

设计要点：

- **唯一索引 `uk_user_product_type`**：同一用户对同一商品的同类行为只保留一行，
  重复发生只累加 `behavior_count` 并刷新时间 —— 避免"浏览"把行为表撑爆，同时保留频次信号；
- **埋点旁路化**：行为记录写失败不能影响收藏/下单等主业务，所有埋点调用点都做了异常吞掉处理；
- **离线回填**：已存在的收藏、订单、私信行为由 `db_v011_recommend.sql` 一次性回填，
  上线即有数据可用，无需等待用户重新产生行为。

## 三、算法设计

### 3.1 三路召回

**① 协同过滤（Item-CF，基于物品）**

```
sim(i, j) = co(i, j) / sqrt(pop(i) × pop(j))          —— 物品相似度（余弦）
score_cf(u, j) = Σ_{i ∈ I(u)} interest(u, i) × sim(i, j)
interest(u, i) = weight × sqrt(behavior_count) × 0.5^(Δdays / halfLife)
```

- `co(i,j)`：同时对 i、j 产生过行为的**去重用户数**（由 SQL 聚合，只按"该用户交互过的商品"限定范围）；
- `pop(i)`：商品 i 的行为人数；
- 时间衰减 `0.5^(Δdays/halfLife)`：半衰期默认 30 天，越久远的行为影响越小。

**② 内容匹配**

```
score_content(u, j) = 0.55 × 分类偏好匹配 + 0.30 × 价格相近度 + 0.15 × 校区一致
分类偏好匹配 = 用户在该分类的加权兴趣 / 最大分类兴趣          （归一化到 0~1）
价格相近度  = exp(-|price_j - μ_u| / (σ_u + 1))              （μ、σ 为用户历史交互商品价格的加权均值与标准差）
```

**③ 热门度**

```
score_hot(j) = (0.50×log(1+浏览量) + 0.30×log(1+收藏量) + 0.20×log(1+行为人数)) × (0.70 + 0.30×新鲜度)
```

### 3.2 融合与后处理

```
score(u, j) = w_cf × cf_norm + w_content × content_norm + w_hot × hot_norm      （每路先做 min-max 归一化）
默认权重：w_cf = 0.50，w_content = 0.35，w_hot = 0.15（可在 application.yml 调整）
```

后处理规则（保证结果可用、可解释、不重复）：

| 规则 | 说明 |
| --- | --- |
| 过滤 | 只推荐**在售**商品；排除**自己发布**、**已收藏**、**已下单**的商品（待交易/已完成） |
| 降权 | 仅浏览过但未收藏/未下单的商品，得分 × 0.55（用户可能仍想买，不完全排除） |
| 多样性 | 同一分类最多 3 条，不足时再按得分用溢出项补齐 |
| 冷启动 | 未登录 / 无行为 → 纯热门（返回 12 条） |
| 可解释 | 每条结果给出**来源标签**（协同过滤 / 内容匹配 / 同类目热门 / 混合召回）与**推荐理由**（"和你关注过的《X》相似""你常看「教材书籍」"） |

### 3.3 接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/product/recommend?size=8&strategy=auto` | 猜你喜欢。登录后个性化，未登录热门冷启动 |
| `GET /api/product/similar/{id}?size=6` | 相似商品（详情页相关推荐），相似物品不足时用**同父分类**热门补齐 |

`strategy` 取值：`auto`（默认融合权重）/ `hot` / `content` / `cf` / `hybrid` /
`hybrid-cf`（偏协同 0.7/0.2/0.1）/ `hybrid-content`（偏内容 0.3/0.6/0.1）。
**同一套过滤规则适用于所有策略**，因此可以直接用于离线对比实验与线上 A/B 测试。

## 四、离线评测实验

### 4.1 实验设置

| 项目 | 设置 |
| --- | --- |
| 评测协议 | **留一法（Leave-One-Out）**：每个用户留出最后一次行为对应的商品作为 ground truth，从行为表删除后再推荐 |
| 数据集 | **仿真数据集**（`tools/recommend-eval.py` 生成，随机种子 20261003，可复现） |
| 数据规模 | 60 个用户 / 80 件仿真商品 + 14 件演示商品 = **92 件候选在售商品**，655 条行为 |
| 数据分布 | 4 个兴趣主题（对应真实分类树的一级分类：教材书籍/数码电子/生活用品/运动户外）；每个用户 80% 行为集中在主主题；活跃用户 36 人（7~11 条行为）、稀疏用户 24 人（2~3 条行为） |
| 评测指标 | HitRate@K（留出商品是否出现在 Top-K）、Precision@K、覆盖率（去重推荐商品/候选总量）、平均响应时间 |
| K | 10 |
| 评测方式 | 调用**真实推荐接口**（非离线重实现），保证评测与实际线上行为一致 |

> 为什么用仿真数据：演示库只有 4 个用户 / 14 件商品，共现矩阵几乎为空，无法支撑算法对比；
> 仿真数据严格按"校园二手交易"的分布特征生成（兴趣主题与真实分类树对应），
> 且随机种子固定，任何人重跑都能得到同样结果。

### 4.2 实验结果

**总体对比（60 个评测用户，Top-10）**

| 召回策略 | HitRate@K | Precision@K | 覆盖率 | 去重商品数 | 平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 纯热门（基线） | 8.33% | 0.83% | 11.96% | 11 | 29.3 ms |
| 纯内容匹配 | 25.00% | 2.50% | 92.39% | 85 | 65.9 ms |
| **纯协同过滤** | **36.67%** | **3.67%** | 81.52% | 75 | 70.2 ms |
| 融合 0.50/0.35/0.15（默认） | 35.00% | 3.50% | 82.61% | 76 | 71.0 ms |
| 融合 0.70/0.20/0.10（偏协同） | 31.67% | 3.17% | 81.52% | 75 | 69.6 ms |
| 融合 0.30/0.60/0.10（偏内容） | 35.00% | 3.50% | 86.96% | 80 | 70.3 ms |

**分场景对比（数据稀疏度）**

| 召回策略 | 活跃用户 HitRate@K（36 人） | 稀疏用户 HitRate@K（24 人） |
| --- | ---: | ---: |
| 纯热门（基线） | 7.69% | 9.52% |
| 纯内容匹配 | 30.77% | 14.29% |
| 纯协同过滤 | **41.03%** | 28.57% |
| 融合 0.50/0.35/0.15 | **41.03%** | 23.81% |
| 融合 0.70/0.20/0.10 | 33.33% | 28.57% |
| **融合 0.30/0.60/0.10（偏内容）** | 35.90% | **33.33%** |

### 4.3 结论（可直接写进论文）

1. **个性化显著优于热门基线**：HitRate@K 从 8.33% 提升到 36.67%（**+28.34 个百分点，相对提升约 3.4 倍**），
   说明"按用户行为推荐"在校园二手场景确实有效；
2. **覆盖率大幅提升**：热门基线的 Top-10 只覆盖 11.96% 的商品（头部效应严重），
   个性化策略覆盖 **80% 以上**，长尾商品获得曝光，有助于提高整体成交率；
3. **协同过滤在行为充足时最强**（活跃用户 41.03%），但在**稀疏用户**上衰减明显（28.57%）；
   纯内容匹配虽然整体较弱（25.00%），却是稀疏场景下"能打出分"的关键一路；
4. **融合策略的价值在于鲁棒性**：`0.30/0.60/0.10`（偏内容）在**稀疏用户上取得最优 33.33%**，
   同时整体仅比最优低 1.67 个百分点 —— 即"用很小的整体损失换取冷启动/稀疏场景的显著提升"，
   这正是在校园场景选择融合方案而非单一算法的实验依据；
5. **耗时可控**：单次推荐平均 70 ms（含三路打分与两次聚合查询），
   热门基线 29 ms 但无个性化；后续可通过"相似度矩阵离线预计算 + Redis 缓存"进一步压缩（见第六章）。

### 4.4 复现方式

```bash
python tools/recommend-eval.py     # 自动：造仿真数据 → 留一法评测 → 输出报表 → 清理数据
```
脚本会在 `tools/recommend-eval-result.json` 留存完整结果（含生成时间、随机种子、逐策略明细），
便于论文附录引用；评测结束后自动清理仿真数据，不影响演示库。

## 五、工程实现要点

| 要点 | 做法 |
| --- | --- |
| 矩阵聚合下推数据库 | 共现矩阵用 SQL 在数据库内聚合，且只按"当前用户交互过的商品"限定范围，结果集 O(用户行为数 × 平均共现数)，不全量加载行为表 |
| 算法参数外置 | 权重、半衰期、候选池、多样性上限等 14 个参数放在 `campus.recommend.*`，调参不改代码 |
| 策略可切换 | `strategy` 参数支持单路消融与三档融合权重，同一套过滤规则保证可比性 |
| 埋点旁路 | 所有埋点调用点异常吞掉，行为表故障不影响商品浏览/收藏/下单 |
| 可解释输出 | 每条推荐返回来源标签、三路得分与推荐理由，前端直接展示 |
| 测试覆盖 | 21 条用例覆盖接口、算法规则（排除/冷启动/多样性/排序）、数据层（埋点幂等、权重） |

## 六、后续可优化方向（论文"展望"可用）

1. **离线预计算 + 缓存**：把物品相似度矩阵与时下热门榜离线算好写入 Redis，线上只做打分与排序，
   预计可将平均耗时降到 10 ms 量级；
2. **行为序列建模**：引入用户行为时间序列（如 Session 内序列），尝试 Item2Vec / 简单深度模型；
3. **多目标排序**：把"成交率""回复率"作为线上反馈信号，用 CTR/CVR 加权替代人工权重；
4. **A/B 实验平台**：利用现有 `strategy` 参数按用户分桶，统计点击率、收藏率、下单转化率等在线指标；
5. **冷启动画像**：新用户注册时选择兴趣分类，直接完成内容冷启动；
6. **实时特征**：结合"最近 1 小时浏览"做实时召回，缓解兴趣漂移。
