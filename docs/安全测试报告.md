### 关键证据摘录

- **登录注入全部被拒**：`admin' OR '1'='1`、`admin'--`、`admin' OR 1=1 #`、`' UNION SELECT ...`
  四种载荷均返回业务码 `2002`（用户名或密码错误），**没有一种能拿到 token**；
- **时间盲注未生效**：`keyword=' AND SLEEP(3)-- ` 的响应耗时 **2 ms**（若 SQL 被拼接，应显著变慢）
  → 证明数据访问走的是 MyBatis 的**参数化查询**；
- **联合查询不泄露用户表**：响应中既无密码哈希（`$2a$`）也无用户名字段；
- **注入后数据完好**：分页参数塞入 `1;DROP TABLE product--` 之后，商品表仍可正常查询（13 条）；
- **JWT 三类攻击全部被拒（401）**：篡改 payload 保留签名、`alg=none` 无签名 token、签名被改；
- **横向越权 6004**：用户 A 查看用户 B 的订单被拒，而 B 自己查看正常（对照组，排除"接口整体不可用"的假通过）；
- **纵向越权 403**：普通用户访问管理端仪表盘 / 用户列表 / 操作日志均被拒，管理员访问正常（对照组）；
- **错误响应不含堆栈**：无 `Exception` / `at com.campus` / `java.lang` / `org.springframework` 片段；
- **商品详情不泄露卖家手机号与邮箱**（正则匹配 `1[3-9]\d{9}` 与邮箱格式均为 False）。

## 三、★ 发现的问题与处理（本节是本次安全测试最有价值的部分）

### 3.1 已修复：错误的 Content-Type 返回 500（伪装成"服务端故障"）

**现象**：向 `/api/user/login` 发送 `Content-Type: application/x-www-form-urlencoded`
（接口要求 JSON）时，返回**业务码 500**。

**定位**：Spring 抛的是 `HttpMediaTypeNotSupportedException`，而 `GlobalExceptionHandler`
当时没有为该异常定义处理分支，于是落到了最后的**兜底分支**（`@ExceptionHandler(Exception.class)`），
统一按"服务器内部错误"返回。

**为什么算问题**：这是**客户端用法问题**，应明确告知调用方（4xx 语义），
返回 500 会误导前端与监控（把使用错误统计成服务端故障）。

**修复**：在全局异常处理器中新增分支，返回 400 参数错误并给出可读提示
「请求体类型不受支持，请使用 application/json」；
同时补单元测试 `GlobalExceptionHandlerTest#mediaTypeNotSupported` 锁定该行为。
回归后该用例通过（`code=400`）。

> 注：这里沿用统一响应的 **400 参数错误码**，而不是新增 415：
> 项目接口约定是"HTTP 200 + 业务码"，前端按业务码分支；新增错误码会扩大前端分支，
> 且会牵动「错误码枚举不变量」这条已冻结的契约测试。

### 3.2 已修复：前端开发服务器暴露面（真实风险）

**现象**（依赖审计 + 配置核查）：

- `vite.config.js` 中 `server.host = '0.0.0.0'` —— 开发服务器监听**所有网卡**；
- 本机 `vite = 5.4.21`，命中 **`server.fs.deny` 在 Windows 上可被绕过** 的漏洞
  （GHSA-fx2h-pf6j-xcff，修复版本要求 `>=6.4.3`，**5.x 无补丁**）；
- 叠加 esbuild 的「任意网站可向 dev server 发请求并读取响应」问题
  （GHSA-67mh-4wv8-2f99）。

**风险**：在教室/图书馆等不可信网络下运行 `pnpm dev` 时，同网段的其他设备可连接 5173 端口，
组合上述漏洞存在**读取本机文件**的风险。

**修复**：把 `host` 改为 `'127.0.0.1'`（只监听回环地址），并在注释中写明原因与按需开启方式：

```bash
# 真机/手机调试时临时开启（用完即关，不要长期挂着）
pnpm dev --host 0.0.0.0
```

**影响面确认**：改的是**开发服务器**；生产由 Nginx 托管 `frontend/dist` 构建产物
（`root D:/campus-secondhand-trade/frontend/dist; try_files ...`），**根本不运行 vite**，
因此生产环境不受该漏洞影响。改后已重新 `pnpm build`（19.97s 成功）并验证站点正常（HTTP 200、`#app` 挂载点存在）。

### 3.3 已修复：写接口限流覆盖缺口（★ 其中一个能绕过登录限流）

v0.18 新增**写接口限流覆盖检查**（`tools/check-ratelimit.py`，已接入 CI，阈值锁死 0），
把"所有 POST/PUT/DELETE 接口是否都有限流"从"靠人记得加"变成"可检查的事实"。
首次运行就发现 **2 处真实缺口**：

| 接口 | 问题 | 严重程度 |
| --- | --- | --- |
| `POST /api/auth/login` | ★ 别名接口**没有限流**，而等价的 `/api/user/login` 有 → 可用它**绕过登录限流做暴力破解**；前端 `api/common.js` 调用的恰是这个别名 | **高** |
| `PUT /api/product/status` | 上架/下架接口未限流，可被反复调用扰动列表并触发缓存失效 | 中 |

两处均已按"与同类接口一致的参数"修复。修复后实测：

```
写接口限流覆盖检查：共 22 个写接口（POST/PUT/DELETE）
  已加 @RateLimit     : 12
  白名单（有意不加）  : 10   ← 管理员专属接口（每次写 admin_log 审计）+ 幂等的退出登录 + 受文件大小约束的上传
  ★ 未限流且无理由    : 0
```

> 白名单本身也是文档：每个"有意不加限流"的接口都在脚本里写明了理由 ——
> 因此这个检查不能被"懒得加"绕过：**要么加限流，要么写清为什么可以不限**。

### 3.4 待排期：前端 4 条依赖漏洞（均为开发期构建工具）

`pnpm audit` 结果：`info 0 / low 0 / moderate 3 / high 1`，**全部集中在 `vite` 与 `esbuild`**，
即**构建期依赖**，不会被打包进生产产物。

- 唯一彻底解法是把 vite 升到 **>=6.4.3**（5.x 无补丁），属于**构建工具大版本跳跃**，
  不宜在答辩前临时进行；
- 已通过 3.2 消除**实际暴露面**（dev server 不再对外监听），风险等级降为"仅本机可触发"；
- 建议后续排期：升级 vite + `@vitejs/plugin-vue` 后，按顺序验证
  ① `pnpm build` 成功 ② 前端单测 ③ 端到端用例 ④ 部署站点回归，再合并。

> **如实说明（v0.18 更新：已实际尝试运行，被环境前置条件阻塞）**
>
> 2026-10-16 两次执行 `./mvnw org.owasp:dependency-check-maven:check`，
> 均在**更新漏洞库阶段**失败，报错原样摘录如下：
>
> ```
> [ERROR] Error updating the NVD Data
>   Caused by: NvdApiException: Invalid API Key, length of 0 too short to provided a masked partial key
> [ERROR] Failed to initialize the RetireJS repo
>   Caused by: javax.net.ssl.SSLHandshakeException: PKIX path building failed:
>     unable to find valid certification path to requested target
> ```
>
> 两个都是**环境前置条件**，不是代码问题：
>
> 1. **NVD 现已强制要求 API Key** —— 没有 key 就无法下载漏洞库
>    （免费申请：<https://nvd.nist.gov/developers/request-an-api-key>）；
> 2. **JDK 信任库缺少可信根证书** —— 本机开着网络加速工具（HTTPS 拦截），
>    `raw.githubusercontent.com` 的证书链无法通过 JDK 信任库校验。
>
> 结论：**本地 OWASP 扫描在本机环境下跑不通**（两个前置条件都不满足），这一点不回避。
> v0.18 起改为采用下面的**零成本自动化方案**（4.3）；本地 OWASP 保留为
> "需要一份可离线归档的 HTML 报告"时的备选路径。
>
> 备选路径的补齐方式（将来若要跑）：
>
> ```bash
> # ① 申请 NVD API Key 后设置环境变量，再跑：
> set NVD_API_KEY=xxxxxxxxxxxxxxxx
> cd backend && ./mvnw org.owasp:dependency-check-maven:check
> #    报告：backend/target/dependency-check-report.html
> # ② 若仍报 PKIX 错误：先关闭网络加速的 HTTPS 拦截，
> #    或把拦截所用的根证书导入 JDK 的 cacerts 后重跑
> ```

### 4.3 ★ 已采用的自动化方案：GitHub Dependabot

**为什么选它**：本地扫描卡在"API Key + 证书"两个环境前置条件上，而 Dependabot 是
GitHub 原生能力 —— **零安装、零密钥、零证书问题**，数据来自 GitHub Advisory Database
（同时覆盖 **Maven 与 npm**），长期自动运行，比一次性本地报告更适合本项目。

**已做的事**：仓库根目录新增 [`.github/dependabot.yml`](../.github/dependabot.yml)，配置了三个生态：

| 生态 | 目录 | 频率 | 说明 |
| --- | --- | --- | --- |
| `maven` | `/backend` | 每周一 06:00 | 按 Spring / 数据库 / 认证与 JSON 分三组提 PR，避免版本错配导致启动失败 |
| `npm` | `/frontend` | 每周一 06:00 | 构建工具（vite/esbuild）单独成组；**vite 主版本跳跃不自动提 PR**（需人工排期验证） |
| `github-actions` | `/` | 每月 | 避免 CI 里用的 Actions 长期停留在有漏洞的旧版本 |

**还需一次点击**（本文件负责"版本更新 PR"，漏洞告警另有开关）：

> 仓库 → **Settings → Code security**（或 Advanced Security）→ 打开 **Dependabot alerts**

打开后，仓库 **Security → Dependabot** 标签页会列出所有命中已知漏洞的依赖
（含 CVE 编号、严重度、修复版本），这正是论文安全测试章节可直接引用的
"自动化依赖漏洞扫描"证据。

**因此本项目的依赖漏洞扫描现状（v0.18）**：

| 范围 | 方式 | 状态 |
| --- | --- | --- |
| 前端依赖 | `pnpm audit`（本地，随时可重跑） | ✅ 实测 `moderate 3 / high 1 / critical 0`，全为 vite/esbuild **构建期**依赖 |
| 前端 + 后端依赖 | **GitHub Dependabot**（仓库内自动运行） | ✅ 配置已提交；开启 alerts 后即生效 |
| 后端依赖 | 直接依赖清单 + 公开披露信息**人工核查** | ✅ 已确认 log4j-core / fastjson / commons-collections / struts / xstream 均未引入 |
| 后端依赖 | OWASP dependency-check（本地全自动） | ⚠️ 环境前置条件不满足，已如实记录，保留为备选路径 |

## 五、结论

1. **注入类风险可控**：登录绕过 4 种载荷全部被拒，时间盲注未生效（参数化查询），
   联合查询不泄露用户表，注入尝试后数据表完好；
2. **认证与授权边界清晰**：无凭证 401、JWT 三类篡改 401、横向越权 6004、纵向越权 403，
   且每组都带**对照组**（合法用户/管理员访问正常），避免"接口整体不可用"造成的假通过；
3. **不泄露敏感信息**：响应无密码字段、无异常堆栈；运维端点在生产不可访问
   （经 Nginx 的 `/actuator/*` 落到前端 SPA 且**不含任何 actuator 数据**；
   真正的管理端口 8090 上 `env/beans/heapdump/shutdown` 均为 404）；
4. **发现并修复了 2 个真实问题**（异常处理缺口、开发服务器暴露面），
   修复均有回归证据；第 3 项（构建工具依赖升级）已给出路径与验证清单。

### 局限（如实说明）

- 本次是**用例化安全测试**，不是完整的渗透测试与代码审计；
- 未覆盖：业务逻辑漏洞的对抗性挖掘（如并发下的业务竞态）、文件上传的类型/内容校验深度、
  越权矩阵的穷举（本次覆盖了订单与商品两条关键路径）；
- 依赖扫描以后端人工核查 + 前端自动化审计为主，详见 4.2 的说明。
