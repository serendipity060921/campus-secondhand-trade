# 长稳测试（soak，v0.18 / 第4批-⑮）

> 一句话结论：5 分钟混合读写共 **37,741 次请求**，**0 个 5xx、0 次网络错误**；
> p95 从首窗 24.9ms 到末窗 25.2ms（**漂移 1.01 倍**）；JVM 堆内存 201.1 → 211.1 MB（**+5.0%**），
> 无线程增长、无内存泄漏迹象。跑完演示数据不变量仍通过。

- 实测时间：2026-10-16
- 环境：prod profile，`http://127.0.0.1:8080`，actuator `127.0.0.1:8090`
- 工具：`tools/soak-test.py`（零第三方依赖）
- 原始数据：`docs/test-evidence/长稳测试-数据.json`

---

## 一、长稳要回答的问题，和压测不一样

⑭ 的多账号压测回答的是"**并发那一瞬间**对不对"（会不会超卖、会不会撞唯一索引）。
它看不出的问题，恰好是长稳才能暴露的：

| 隐患 | 为什么短压测看不出来 |
| --- | --- |
| 内存泄漏 | 几分钟内堆还没涨到触发 OOM 的程度 |
| GC 抖动 | 需要积累够多对象才会出现 Full GC |
| 连接池耗尽 | 泄漏的连接要跑一会儿才攒满 |
| 越跑越慢 | 可能是慢查询累积、缓存命中率下降、日志/临时文件增长 |
| 线程泄漏 | 短时间线程数看不出单调上升 |

## 二、方法

### 2.1 混合负载（读 7 : 写 3）

- **读**（随机轮换）：商品列表 / 详情 ×2 / 热门榜 / 分类树 / 个性化推荐；
- **写**：用 `stu_demo` 对同一件商品做「**收藏 ↔ 取消收藏**」来回切换。

### 2.2 写操作为什么要"净零"

长稳会跑几万次请求，如果每次都写新数据，跑完数据库就被污染了。
所以写路径选的是**自己会抵消的操作**，并且：

> 目标商品是脚本**现挑的"该账号尚未收藏过"的在售商品**
> （先查 `/api/favorite/list` 排除已收藏的），保证第一次操作是"收藏成功"而不是 4001，
> 交替之后**净变化恰好为 0**。

实测结果：跑完 `seed-demo-data.py --verify` 仍然
`user 4 / product 17 / favorite 4 / orders 4 / message 9` ✅

### 2.3 采样

每 30 秒一个窗口，记录窗口内的请求数、p50 / p95 / max 延迟、5xx、网络错误；
同时读 actuator 的 `jvm.memory.used`（字节）作为堆内存口径。

## 四、两个值得单独说明的点

### 4.1 一次 158.8 ms 的尖刺（max 远高于 p95）

180s 窗口出现过一次 158.8ms 的最大延迟，而该窗口 p95 只有 24.0ms。
这正说明**长稳要看 max 而不是只看 p95**：

- 尖刺没有持续（下一窗 max 回到 71.4ms），因此不是"越跑越慢"；
- 最可能是 **Young GC** 或**某次缓存重建**（缓存失效后第一个请求需要回源查库）；
- 若 max 单调上升，就应当怀疑连接池或慢查询累积。

这条记录保留在数据里，不做平滑处理。

### 4.2 两个内存口径不一致是正常的

| 口径 | 数值 | 含义 |
| --- | ---: | --- |
| actuator `jvm.memory.used`（堆） | 201.1 → 211.1 MB | Java 堆内对象 |
| 进程 RSS（OS 视角） | 360.5 → 394 MB | 堆 + 元空间 + 线程栈 + 直接内存 + 代码缓存 |

RSS 比堆大约 180 MB 属于正常（Metaspace、约 100 个线程的栈、Netty/JDBC 的直接内存等）。
**两个口径都要记**：只看堆会漏掉堆外泄漏，只看 RSS 会把正常的 JIT/类加载当成泄漏。

## 五、局限（如实说明）

1. **5 分钟不是真正的"长稳"**：真机上建议跑 1~2 小时再下结论；
   本项目受答辩准备时间限制先跑 5 分钟，并把脚本参数化（`--minutes 60` 即可延长）。
2. **单实例**：没有验证多实例下的连接池/内存行为。
3. **负载形状是合成的**：7:3 读写、6 个读接口轮换，不代表真实用户轨迹；
   真实流量有早晚高峰与突发。
4. **未注入故障**：没有在长稳过程中制造"Redis 断开 / MySQL 慢查询"，
   这类演练建议配合第 5 批的 CI 环境或专门的混沌测试做。

## 六、复现
