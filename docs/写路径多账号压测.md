# 写路径多账号压测（v0.18 / 第4批-⑭）

> 一句话结论：**并发抢购 3 轮，每轮 4 个账号同时抢同一件商品，每轮恰好 1 单成交**（不超卖）；
> 同一账号 20 次并发收藏只落 1 条记录；限流按账号生效；全程 **0 个 5xx**。

- 实测时间：2026-10-16
- 环境：prod profile，`http://127.0.0.1:8080`
- 工具：`tools/stress-write.py`（零第三方依赖）
- 原始数据：`docs/test-evidence/写路径压测-数据.json`

---

## 一、为什么必须"多账号"

本项目**所有写接口都按账号维度限流**：

| 接口 | 限流 |
| --- | --- |
| 发布商品 | 10 次 / 300 秒 / 账号 |
| 下单 | 10 次 / 300 秒 / 账号 |
| 收藏 | 60 次 / 60 秒 / 账号 |
| 商品状态变更 | 20 次 / 300 秒 / 账号 |
| 注册 | 10 次 / 300 秒（按 IP） |

如果用单账号压，
第一个撞上的会是**限流器**（429），测出来的是"我的限流生效了"，
而不是"写路径在高并发下是否正确"。所以脚本先注册一批一次性账号，把压力摊开。

## 二、四个场景与结果

### S1 并发抢购同一件商品 → **必须恰好 1 单成交**（★ 最重要）

| 轮次 | 商品 | 并发账号 | 成功下单(code=200) | **实际成交** | 商品后续状态 | p95 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 第 1 轮 | #567 | 4 | 1 | **1** | 4（交易中） | 29.7 ms |
| 第 2 轮 | #568 | 4 | 1 | **1** | 4（交易中） | 14.2 ms |
| 第 3 轮 | #569 | 4 | 1 | **1** | 4（交易中） | 18.5 ms |

其余账号全部拿到 `6001 商品已下架或已被预订`。

**机理**：下单不是"先查再改"，而是**条件更新**：

```java
int locked = productService.getBaseMapper().update(null,
        new LambdaUpdateWrapper<Product>()
                .set(Product::getStatus, PRODUCT_TRADING)
                .eq(Product::getId, productId)
                .eq(Product::getStatus, PRODUCT_ON_SALE));     // ← 关键：状态必须仍是"在售"
if (locked != 1) { /* 没抢到 */ }
```

只有 `UPDATE` 影响行数 == 1 的请求才算抢到，其余全部失败。
**这是数据库层面的原子操作**，不需要分布式锁、也不会因为"两个请求同时通过检查"而超卖。

★ 判定方式特意做了"双证据"：不只看返回码，还逐个查每个账号的「我买到的」里是否真有该商品。
只看返回码有可能被"服务端返回 200 但事务回滚"骗过去。

### S2 同一账号 20 次并发收藏 → **恰好 1 条记录**

| 指标 | 结果 |
| --- | --- |
| 成功（200） | **1** |
| 重复收藏被拒（4001） | **19** |
| 商品 favoriteCount | **1** |
| 5xx | **0** |

机理是"先查再插 + 数据库唯一索引 `uk_user_product`"双保险：
并发下两个请求可能同时通过查重，此时唯一索引兜底，
并把 `DuplicateKeyException` 转成业务码 4001（而不是通用的"数据已存在 1002"）。

### S3 限流按账号生效，不是全局

| 场景 | 结果 | 说明 |
| --- | --- | --- |
| 3 个账号各并发发 5 件 | **各 5/5 全成功** | 若限流是全局键，第 11 次就会被拦 |
| 单账号连发 12 件 | **5 成功 + 7 次 429** | 单账号上限（10/300s，其中 5 次是刚用过的额度）确实生效 |

两组合起来才说明限流键**包含账号** —— 只测其中一个都会得出错误结论。

### S4 全程 0 个 5xx

所有场景（抢购 / 收藏 / 发布 / 爆限流）累计 **HTTP 5xx = 0**。
并发下没有出现死锁、连接池耗尽或未捕获异常。

## 三、实测中遇到的两件"计划外的事实"（如实记录）

1. **机审 PASS 的商品会直接上架，不走人工审核**
   脚本最初在发布后固定调一次"管理员审核"，结果拿到 `8003 只有「待审核」状态的商品才能审核`。
   反查发现：内容机审通过的发布请求**直接是"在售"状态**，根本不需要审核。
   于是把审核改成"已上架则跳过"（容忍 8003）。
   —— 这不是缺陷，而是"机审已放行、人工只处理可疑件"的设计。

2. **注册限流按 IP**：本次计划 6 个买家，实际只注册成功 4 个
   （注册 10 次/300 秒按 IP 计数，上一轮压测已消耗部分额度）。
   因此 S1 的并发度是 4 而不是 6 —— 数字按实际发生写，不做修饰。

## 四、数据卫生

压测会**创建真实数据**（新账号、商品、订单、收藏）。跑完必须恢复：

```bash
python tools/seed-demo-data.py --verify    # 压测后：user 14 ✗ 期望 4（确认被污染）
python tools/seed-demo-data.py --reset     # 按基线恢复
python tools/seed-demo-data.py --verify    # 再次核对：user 4 / product 17 / favorite 4 / orders 4 / message 9 ✅
```

实测过程：`user` 从 4 涨到 14，reset 后回到 4，其余基线（product 17 / favorite 4 / orders 4 / message 9）全部恢复。
**这也是部署验证用例的数据完整性断言能复跑的前提。**

## 五、局限（如实说明）

1. **单机、单实例**：并发度只有 4~20，且请求都打到同一个 JVM。没有验证多实例下的
   分布式竞争（那需要 Nginx 多后端 + 共享 MySQL/Redis）。
2. **只覆盖写路径的关键几类**：下单/收藏/发布/状态变更；
   未覆盖"取消订单与确认完成并发"这类**状态竞争**（属并发一致性，需要更多场景编排）。
3. **p50/p95 只是本机局域网数字**，不代表公网延迟；容量结论见
   [`性能测试报告-缓存击穿与写路径.md`](性能测试报告-缓存击穿与写路径.md)。
4. 压测脚本**不做清理**（刻意）：清理交给 `seed-demo-data.py --reset`，
   避免脚本"以为自己删干净了"却在某个异常分支留下脏数据。

## 六、复现

```bash
# 默认 6 个买家、1 轮抢购
python tools/stress-write.py

# 更狠一点：3 轮抢购 + 落盘 JSON
python tools/stress-write.py --buyers 6 --repeat 3 --json docs/test-evidence/写路径压测-数据.json

# 跑完务必恢复
python tools/seed-demo-data.py --reset
```
