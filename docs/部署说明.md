## 二、部署架构

```
                         ┌─────────────────────────────┐
   浏览器 / 移动端 ──────►│  Nginx（80 / 本机 8081）     │
                         │  ① 托管 Vue 打包产物         │
                         │  ② SPA history 路由回退      │
                         │  ③ /api  → 反向代理          │
                         │  ④ /ws   → WebSocket 升级    │
                         └──────────────┬──────────────┘
                                        │ 内网
                         ┌──────────────▼──────────────┐
                         │  Spring Boot（8080，prod）   │
                         │  · JWT 鉴权 / 拦截器          │
                         │  · Redis 缓存 + 限流 + 在线   │
                         └───┬─────────────────────┬────┘
                             │                     │
                    ┌────────▼────────┐   ┌────────▼────────┐
                    │  MySQL 8（3306）│   │  Redis（6379）  │
                    │  10 张表        │   │  缓存/ZSet/限流  │
                    └─────────────────┘   └─────────────────┘
```

**为什么前后端只暴露一个端口？** 前端与接口同源（都经 Nginx），
浏览器侧不存在跨域，也省去一个额外端口；WebSocket 也走同一个域，配置最简。

## 四、路径 A：Docker Compose（推荐生产使用）

### 4.1 镜像加速（国内必配，否则拉取镜像极慢）

在 Docker Desktop → Settings → Docker Engine 中加入（或编辑 `/etc/docker/daemon.json`）：

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1panel.live",
    "https://dockerproxy.net"
  ]
}
```

> 镜像站可用性会变化，若某个失效换下一个；也可直接给镜像加前缀，如
> `docker pull docker.m.daocloud.io/library/mysql:8.4`。

### 4.2 启动

```bash
cd deploy/docker
cp .env.example .env          # 修改里面的密码与 JWT_SECRET
docker compose --env-file .env up -d --build
```

首次启动会自动：建库 → 执行 `db/schema/01-schema.sql` / `db/schema/02-recommend.sql` / `db/schema/03-admin.sql`
（挂在 `/docker-entrypoint-initdb.d/`，按文件名顺序执行）→ 等 MySQL 健康后再起后端。

### 4.3 编排要点（写进论文的工程细节）

| 要点 | 做法 |
| --- | --- |
| 启动顺序 | MySQL/Redis 配 `healthcheck`，后端用 `depends_on: condition: service_healthy`，避免"库还没就绪后端就退出" |
| 数据持久化 | 命名卷 `campus-mysql-data` / `campus-upload-data` / `campus-log-data`，容器重建不丢数据 |
| 构建缓存 | Dockerfile 先 COPY `pom.xml`（后端）与 `package.json`+lock（前端）再 COPY 源码，改代码不重装依赖 |
| 国内构建加速 | 后端 Dockerfile 内置阿里云 Maven 镜像；前端内置 npmmirror；基础镜像可从镜像站拉 |
| 最小权限 | 后端容器用非 root 用户 `campus` 运行 |
| 端口收敛 | 后端不映射到宿主机，只 `expose 8080`，对外仅 Nginx 的 80 |
| 健康检查 | 后端 `wget /api/health`；前端 `wget /`；MySQL `mysqladmin ping`；Redis `redis-cli ping` |

## 五、路径 B：Windows 原生一键部署（✅ 已实测）

### 5.1 前置

- MySQL 与 Redis 已作为 Windows 服务运行（本项目环境：`MySQL84`、`RedisCampus`）
- 后端 jar 已打包：`cd backend && mvnw.cmd -DskipTests package`
- 前端产物已构建：`cd frontend && pnpm build`
- Nginx for Windows 解压到某目录（本项目：`D:\major\tool\nginx-1.27.5`）

### 5.2 一条命令启动

```powershell
powershell -ExecutionPolicy Bypass -File deploy\windows\start.ps1
```

脚本依次完成：① 检查 3306/6379 → ② 首次运行**自动生成 JWT 密钥**并写入 `deploy/windows/env.ps1`
（该文件含密钥，已被 `.gitignore` 忽略）→ ③ 用 prod 配置启动 jar 并等待健康检查 →
④ 启动 Nginx → ⑤ 打印访问入口。

停止：

```powershell
powershell -ExecutionPolicy Bypass -File deploy\windows\stop.ps1
```

## 六、生产配置清单（环境变量）

| 变量 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_DB` | 否 | 127.0.0.1 / 3306 / campus_trade | 数据库连接 |
| `MYSQL_USER` / `MYSQL_PASSWORD` | **是** | campus / 无 | 生产用最小权限账号（见 6.1） |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | 否 | 127.0.0.1 / 6379 / 空 | 公网部署必须设密码 |

| `CORS_ORIGINS` | 否 | http://localhost | 正式域名，多个逗号分隔；**WebSocket 握手也校验它** |
| `SERVER_PORT` | 否 | 8080 | 后端端口 |
| `UPLOAD_PATH` / `LOG_PATH` | 否 | ./uploads / ./logs | 容器部署时指向挂载卷 |
| `AUDIT_ENABLED` | 否 | true | 生产建议"先审后发" |
| `CACHE_ENABLED` | 否 | true | 关闭后走降级路径（压测对照用） |
| `HEALTH_DETAIL_ENABLED` | 否 | false | 关闭 `/api/health/db` 库表统计探针 |

| 场景 | 操作 |
| --- | --- |

| 回滚 | 保留上一版 `dist` 与 jar，替换回去重启即可；数据库改动前先备份 |

## 十、部署踩坑记录（都已在配置里修掉）

### 坑 1：`/health` 经 Nginx 返回 Tomcat 400 Bad Request

- **现象**：`/api/**` 一切正常，但运维探针 `/health` 稳定返回 400（Tomcat 错误页）。
- **原因**：`upstream` 配了 `keepalive 32`，而 `location = /health` 里没有配
  `proxy_http_version 1.1;` 与 `proxy_set_header Connection "";`。
  Nginx 复用上游连接时仍按 HTTP/1.0 语义发送，Tomcat 判定请求非法 → 400。
- **修复**：把这两个头（以及 `Host`/`X-Real-IP`/`X-Forwarded-*`）**提到 server 级统一下发**，
  各 location 继承，只有 `/ws/` 覆盖 `Connection: upgrade`。
- **启示**：用 `upstream keepalive` 就必须配套上面两个设置；代理头集中放 server 级还能避免"漏配"。

### 坑 2：80 端口起不来（`bind() failed (10013)`）

- **现象**：Nginx 配置语法通过，但无法监听 80。
- **定位**：`netstat -ano | findstr :80` 显示 **Steam++（Watt Toolkit 加速器）** 占用了 `0.0.0.0:80`。
- **处理**：本机改用 **8081**（配置里一行 `listen`），生产环境用 80；
  文档中注明排查命令，避免以后误判为"Nginx 装坏了"。

### 坑 3：PowerShell 脚本在 Windows PowerShell 5.1 下语法报错

- **现象**：`start.ps1` 用 PS 5.1 执行报"缺少右 }"，但用 PowerShell 7 却正常。
- **原因**：脚本是**无 BOM 的 UTF-8**，PS 5.1 会按系统 ANSI 代码页解码，中文注释被打乱，
  进而把花括号/引号误判。
- **修复**：脚本保存为 **UTF-8 with BOM**（并加了自动化校验：用 PS 解析器 `ParseFile` 检查语法）。
- **启示**：给 Windows 用户用的 `.ps1` 一律带 BOM；中文注释多的脚本尤其要注意。

### 坑 4：E2E 脚本硬编码开发端口导致 IndexError

- **现象**：端到端脚本在 5173 下 31/31 通过，换成 Nginx 的 8081 后 5 条用例报
  `IndexError: list index out of range`。
- **原因**：脚本里写了 `A.url.split('5173')[1]` 来截取路径，端口一变 split 只剩一段。
- **修复**：改为 `A.url.replace(BASE, '')`，并支持 `E2E_BASE` / `API_BASE` 环境变量指定入口，
  使测试脚本与部署形态解耦 → 换成 8081 后 **31/31 通过**。
